### 2.1 数据层专项实测（2026-09）

**B2 到底错在哪 —— 比报告里写的严重**

| 位置 | ST 5% | 北交所 30% | 用什么当昨收 |
|---|---|---|---|
| `database/downloader/meta.py` | 有 | **无** | **`close.shift(1)`** ✗ |
| `scripts/daily_update.py` | 无 | 只认 `920` | **`close.shift(1)`** ✗ |
| `scripts/rebuild_limit.py` | 有 | `920/43/83/87/88` | 官方 `pre_close` ✓ |

`close.shift(1)` 是**未除权的上一日收盘** —— 10 送 10 的情况下算出的涨跌停价会差一倍。
而增量更新 `daily_update.py` 会拿它去**覆盖** `rebuild_limit.py` 生成的正确数据。

**量化影响**：现有 `cleaned/limit_price` 的 1,596 万行里，有 **1,152,719 行（7.2%）**
是错的 —— 创业板在 2020-08-24 之前被按 ±20% 计算，实际应是 ±10%。
方向上**让回测偏乐观**：涨停价偏高 → 少拦买入；跌停价偏低 → 少拦卖出。

**修复内容**（`database/limit_rules.py`，唯一实现）：
1. 三处调用方统一转调它，并加测试断言"不再各自实现、不再用 `close.shift(1)`"
2. 补上 **创业板 2020-08-24 注册制改革前 ±10%**（三套实现都没有）
3. 北交所统一为 `920/43/83/87/88`
4. 一律用**官方 `pre_close`**；缺这一列时**直接报错**，绝不退化成 `close.shift(1)`

**B4 的实测结论（已用证据化判据复验）**：仍在上市的 5,570 只股票中，
整年缺口共 **44 段，全部有"交易断裂"或"停牌记录覆盖"证据，0 段疑似数据缺失**。

判据（写进 `validate_data --check completeness`，不再是拍一个阈值）：
- **证据一 · 价格断裂**：缺口前一年在 12 月前就停止交易，或缺口后一年到 1 月后才恢复
- **证据二 · 停牌覆盖**：缺口年份 ≥80% 的交易日有 `suspend_type='S'` 记录

两条互补，缺一不可：`000757`（方向光电）2007-04 停牌、2013-02 才复牌，
整整 5 年没有日线，但 **`frozen/suspend` 里 0 条记录**（`suspend_d` 不记录
"暂停上市"）；而 `002015` 的 2015 年整年停牌（复牌首日 7.55 元跳空）
只能靠停牌记录解释。

**结论**：`mark_done` 粒度为"股票"确实是风险，但**没有造成实际数据缺失**。


**新增四条永久门禁**（`validate_data.py`）：

```bash
python scripts/validate_data.py --check limit         # 涨跌停规则一致性（逐行重算比对）
python scripts/validate_data.py --check completeness  # 年份完整性 + cleaned/frozen 一致性
python scripts/validate_data.py --check status        # 停牌/ST/涨跌停三张面板**非空**
python scripts/validate_data.py --check dates         # VARCHAR 日期列可按 YYYYMMDD 解析
```

### 2.2 停牌数据曾经完全失效（本次发现，已修）

`backtest/panel_data.py::load_status_panels` 里有两个叠加的错误，**都被
`except Exception: sus = pd.DataFrame()` 吞掉**，所以从来没有报错：

1. `frozen/suspend` 是**非年度数据集**（只有占位分区 `year=2005`），
   代码按回测区间拼 `year=2024/*.parquet` → 路径不存在 →
   DuckDB 抛 `IOException`。
2. `suspend.trade_date` 是 **VARCHAR `'YYYYMMDD'`**，不是 DATE。

**后果**：`suspended` 面板恒为空表 → `MarketRules(block_suspended=True)` 拿到
全 False → **停牌股照常买卖**，T+1 与流动性假设被架空。
实测 2024 上半年就有 **1,330 个停牌标记**（192 只股票）被漏掉。

**同时发现同一件事被实现了四遍，口径各不相同**：

| 位置 | 只取 `S` 停牌记录 | 日期处理 | 分区 glob |
|---|---|---|---|
| `backtest/panel_data.py` | — | 当成 DATE ✗ | 按年份区间 ✗ |
| `universe/pool.py` | ✗ 把 `R`(复牌日) 也算停牌 | ✓ | `year=*` ✓ |
| `database/loader.py` | ✗ 把 `R` 也算停牌 | ✓ | `year=*` ✓ |
| `joinquant/data.py` | 依赖上面的 panel | — | — |

`R` 是**复牌日，当天恢复交易**，把它当停牌会在复牌当天错误地禁止买卖。
实测全库 `R` 记录 **24,646 条（占停牌记录 4.51%）**，涉及 3,398 只股票；
其中只有 133 个 (股票, 日) 组合同时存在 `S`，也就是说约
**2.45 万个 (股票, 日) 组合被错误地判定为"停牌不可交易"**。

**修法**：新建 `database/status.py` 作为唯一实现，三处调用方全部转发过去；
`database/config.py` 新增 `year_globs()` 统一分区解析（只列真实存在的分区，
静态数据集忽略区间，数据集起始年份晚于区间起点时也不会拼出死路径）。
`limit_rules.st_mask` 同时接受 `Series` 与 `DatetimeIndex`，`st_panel`
也改为复用唯一的 ST 区间实现（此前是第三份，且失败时静默返回全 False）。
`load_st_intervals` 加缓存并改用 DuckDB 一次扫描（22.8 秒 → 1.75 秒）。

**影响面：不是所有消费方都受影响 —— 这点必须讲清楚，否则会误判成"修复无效"**

| 消费方 | 停牌面板缺失时的行为 | 是否被这个 bug 影响 |
|---|---|---|
| 聚宽移植层 `joinquant/data.py::paused` | 有**兜底**："当日无价格行即视为停牌" | **否**（重跑 v1/v2 结果逐位相同：+121.27% / +257.42%） |
| 组合/多标的引擎 `backtest/multi_engine.py` | `_bar()` 缺字段就跳过检查 | **是**（停牌股完全不受约束） |
| 股票池 `universe/pool.py` | 自己实现过一遍，能读到数据 | 部分是（`R` 复牌日被误判为停牌） |

所以"重跑聚宽策略结果不变"**不能**证明 bug 不存在 —— 它只是被兜底掩盖了。
真正的受害者是组合引擎那条路径。`validate_data --check status` 现在会
直接断言三张面板非空，无论哪个消费方、有没有兜底。

### 2.3 舍入方式：银行家舍入 vs 交易所四舍五入（本次发现，已修）

交易所口径是**四舍五入到分**，而 `round()` / `np.round()` 是**银行家舍入**
（round-half-to-even，恰好 .5 时向偶数靠）。浮点表示还会让结果"看运气"：
`10.05×1.1` 的浮点值略大于 11.055，`round()` 恰好给了对的 11.06；
换成 `11.05×1.1=12.155`（浮点略小）就错成 12.15。

**实测旧 `cleaned/limit_price`：涨停价 2.7%、跌停价 4.4% 的行与交易所口径差 1 分钱**
（1500 万行里约 50 万行）。

**修法**：`database/limit_rules.py` 改为**整数分运算**
（`(pc_cents × K + 5000) // 10000`），与浮点无关。
已核实全库 1,596.8 万行 `pre_close` **全部**落在 0.01 网格上（0 例外），
该前提由 `validate_data --check limit` 永久把关。

**重建后的前后比对**（新旧实现同时重算 15,967,594 行）：

| 变化来源 | 行数 | 占比 |
|---|---|---|
| 创业板 2020-08-24 前 ±10% | 1,152,824 | 7.22% |
| 取整改为四舍五入 | 879,695 | 5.51% |
| **合计有变化** | **2,032,519** | **12.73%** |

重建后**逐行重算 137.6 万行（抽样 300 只）与唯一规则完全一致**，
真倒挂 0 行。顺带发现两个"看似异常其实正确"的情形，已写进判据避免误报：
`limit_up == limit_down` 的 11 行全部是 **≤0.09 元股票的粒度塌缩**
（0.09 元的 ST 股 ±5% 上下限都四舍五入到 0.09）；238 个空值**全部是
`920xxx` 且全在 2023 年之前**（北交所 2021-11 才成立，此前是新三板历史，
`pre_close` 本就是垃圾值 —— 即 C1）。

### 2.4 派生缓存会静默返回旧数据（D5，已修）

`.cache/panel/<start>_<end>/` 原先**只以区间为键**。数据被重建后缓存仍然命中，
回测拿着旧数据算出结论 —— 而这一轮刚好改写了 115 万行涨跌停价，
**不修的话重跑也发现不了**。

**修法**：`database/provenance.py` 新增 `dataset_fingerprint()`，
缓存元数据记录所依赖 5 个数据集（daily / valuation / adjust / limit / suspend）
的「文件数 + 最新 mtime」；任一项变化即作废重载，**没有指纹字段的历史缓存一律作废**。
指纹扫描用 `os.scandir`（0.25 秒，`Path.glob` 要 7 秒，快 28 倍）。

### 2.5 tushare 日期字符串混格式导致静默丢数据（本次发现，已修）

全库审计（新增 `validate_data.py --check dates`）发现日期列**列类型不统一**：

| 类型 | 数据集 |
|---|---|
| `TIMESTAMP` | daily_raw / adjust / valuation / limit_price / index_daily / st.start_date … |
| `VARCHAR` | suspend.trade_date、index_cons.trade_date、dividend.*、financial.ann_date、holders.ann_date、st.end_date … |

更隐蔽的是 **VARCHAR 列内部还混着两种格式**：

```
'20230428'             绝大多数
'2025-06-03 16:01:59'  少数（tushare 自身返回不一致）
```

读取方写 `pd.to_datetime(s, format="%Y%m%d", errors="coerce")` 时，
第二种会**静默变 NaT**，紧接着被 `dropna()` 丢掉 —— 数据无声消失。
实测 `frozen/holders.ann_date` **548,603 行里有 8,152 行（1.49%）** 是这种格式。

另有一个 pandas 陷阱：`pd.to_datetime(series)` **不带 format** 时会
**按第一个元素定格式**，同一批里混两种格式照样漏（`'2025-06-03 16:01:59'`
在前时，后面的 `'2024-01-02'` 会被判成 NaT）。必须用 `format="mixed"`。

**修法**：新建 `database/dates.py::parse_tushare_date()`，
`factors/fundamental.py`（2 处：financial、holders）与 `joinquant/data.py`
全部改走它。检查项也从"必须是 YYYYMMDD"改成"**必须能被解析**"，
混合格式只作提示、不算失败。

数据改了 12.73%（约 203 万行涨跌停价）+ 停牌面板从空表变成有 4,083 只股票，
**结论动了多少？** 用两条既有策略做 A/B（面板缓存已按指纹强制失效、全部重载）：

| 策略 | 指标 | 修复前 | 修复后 | 变化 |

| 多因子·规则组合(80 只) | 样本外年化 | +7.60% | +7.54% | −0.06pp |
| | 样本外夏普 | +0.196 | +0.194 | −0.002 |
| | 样本外回撤 | −31.59% | −31.68% | −0.09pp |
| | 成交笔数 | 12,029 | 12,027 | **−2 笔** |
| 多因子·先验组合(50 只) | 样本外年化 | +9.25% | +9.25% | 0 |

**怎么解读（重要，避免两个方向的误读）**

1. **不能**说"改了 12.73% 的数据却没影响，所以不重要"。这些策略是**月度调仓、
   低换手**，而涨跌停拦截用 `LIMIT_TOL` 容差判定"封板"，1 分钱的价格差

   （`_bar()` 缺字段就跳过检查），它才是受害者 —— 规则组合少掉的 2 笔成交
   正是这条路径上的差异。
3. 真正该担心的是**未来**：一旦做高换手、做 2017–2020 的创业板、或把
   `block_limit_up_buy` 的容差调紧，那 203 万行的错误就会直接体现在收益上。
   现在这个隐患被永久门禁（`--check limit` 逐行重算）挡住了。

### 2.7 上市初期规则（C2）：实现 + 用行情数据反证

原来只按板块常规档位算，次新股上市初期的合法大涨会被当成"封板"而**多拦买入**。

**规则表**（`database/limit_rules.py::LISTING_REGIMES`，按"板块 × 上市日"选制度）

| 板块 | 期间 | 规则 |
|---|---|---|
| 主板 | ~2013-12-12 | 首日**不设涨跌幅** |
| 主板 | 2013-12-13 ~ 2023-04-09 | 首日 ×1.44 / ×0.64（基准=**发行价**） |
| 主板 | 2023-04-10 ~ | 前 5 个交易日**不设涨跌幅** |
| 创业板 | 2009-10-30 ~ 2020-08-21 | 首日不设涨跌幅 |
| 创业板 | 2020-08-24 ~ | 前 5 个交易日不设涨跌幅 |
| 科创板 | 2019-07-22 ~ | 前 5 个交易日不设涨跌幅 |
| 北交所 | 2020-07-27 ~ | 首日不设涨跌幅 |

**实现要点**

- "不设涨跌幅" → `limit_up`/`limit_down` 置 **NaN**。`MarketRules._num()` 对
  NaN 返回 `None` 会**跳过**涨跌停检查，正是"无限制"的语义（已在
  `market_rules.py` 就地写明，避免后人误以为是缺数据）。
- 首日 ±44% 的基准是**发行价**，而 tushare 首日的 `pre_close` 正是发行价 ——
  已实测确认（`002973 侨银股份` pre_close=5.74、high/pre_close−1=+44.08%）。
- ⚠️ ±44% **不是对称的**：上是 +44%、下是 −36%（×1.44 / ×0.64）。
- `daily_update.py` / `downloader/meta.py` 原先有
  `.dropna(subset=["limit_up","limit_down"])`，会把"不设涨跌幅"的行也删掉 ——
  已移除，否则增量更新会与全量重建口径不一致。
- 窗口按**市场交易日**计（`trading_calendar()`），停牌不顺延。

**用真实行情反证**（新增 `validate_data.py --check listing`）

| 情形 | 观测 | 结论 |
|---|---|---|
| 主板 2014–2023 首日 | 1,172 行中 **1,150 行**涨幅落在 [42%, 44.5%]，p50=+44.00% | ±44% 确实封顶 ✓ |
| 主板 2005–2013 首日 | p95=+175%、max=+742% | 确实无限制 ✓ |
| 主板 2024+ 首日 | 80 行中 78 行 > 44%，p50=+211% | 确实无限制 ✓ |
| 科创板前 5 日 | 3,089 行中 634 行 > 20% | 确实无限制 ✓ |
| 创业板 2020-08-24 后 | 3,035 行中 682 行 > 20% | 确实无限制 ✓ |
| 北交所首日 | 340 行中 99 行 > 30%，max=+1667% | 确实无限制 ✓ |

**已知残留（见 C2b）**：3 只**重新上市**股（国机重装 +188.9%、汇绿生态
+122.5%、新城控股 +235.9%）被误套首日 ±44%；另有 6 只 2014-01 上市的主板股
首日最高价落在 +45.2%（比 44% 高 1.1%，具体机制未查明）。

### 2.8 顺带查出的两个真规则错误（都由新门禁抓到）

加 `--check listing` 的"价格不得越过涨跌停"这条**实证**校验后，立刻红了
8,488 行 —— 追下去是两个独立的规则错误，而且都是**老错误**、之前所有校验
都没发现：

**① ST 的 ±5% 被错误地套到了创业板/科创板**

2020-08-24 创业板注册制改革后，**创业板与科创板的"风险警示股票"不再单独
设 5%**，仍按板块的 ±20%；北交所同理。早期 `limit_pct` 给所有 ST 一律 5%，
让这些股票的涨停价**偏低一半以上**。
实测：创业板/科创板越界 5,475 行，`limit_up/pre_close−1` 全部 ≈ 0.05。

**② 主板 ST 的档位在 2026-07-06 从 ±5% 放宽到 ±10%**

这个日期是**从行情数据反推**出来的，不是抄公告：

| 期间 | 主板 ST 股每日 \|pct_chg\| 上限 | 超 5.5% 的行数 |
|---|---|---|
| 2015–2025 全年 | 5.17~5.19% | **0** |
| 2026-06-22 ~ 2026-07-03 | 5.11~5.19% | 0 |
| **2026-07-06 起** | **10.08~10.26%** | 639（134 只股票） |

断点非常干净，因此按制度变更处理（`MAIN_ST_10PCT_FROM`）。同日价格越界
行数从 720 降到 0。**若日后拿到正式公告，核对/修正这一个常量即可。**

**修正后的越界情况**（`--check listing`）

| 指标 | 修正前 | 修正后 |
|---|---|---|
| 最高价 > 涨停价 | 8,488 行 | **302 行（0.0019%）** |
| 最低价 < 跌停价 | 7,527 行 | **1,205 行（0.0075%）** |

残留集中在 **2006–2007**（当年股权分置改革期间的未股改股 S 股**没有涨跌幅
限制**，规则表未建模）与零星的历史个案。门禁改为**比率判据 + 年份归因**
（阈值 0.02%），既能抓住新的系统性错误，又不会因为已知的历史个案永久变红。

### 2.10 全库数据审计（2026-09 第二轮）

对每个数据集做了**新鲜度 + 读取方 + 列一致性**三方面的体检，结论如下。

**① 新鲜度：整体健康，两处小缺口**

| 数据集 | 覆盖 | 状态 |
|---|---|---|
| daily_raw / valuation / adjust / daily_basic / limit_price | ~2026-08-28 | ok |
| financial / holders（`ann_date`） | 2026-08-28 | ok |
| fund_daily / index_daily | 2026-09-15 | ok |
| **etf / options** | 月度快照止于 2026-07-01 | ⚠ **缺 2026-08**（落后 77 天） |
| **northbound** | 仅 2025-05-27 起 | ⚠ 历史未下载 |

> 审计脚本第一版把 `holders` 误报成"落后 411 天"，原因是用了
> `try_cast(ann_date AS TIMESTAMP)` —— `ann_date` 是 VARCHAR `'YYYYMMDD'`，
> 转换全为 NULL，只剩那 8,152 行 ISO 格式的能显示出来。**审计工具自己踩了
> 同一个坑**，改用 `try_strptime` + ISO 兜底后才对。这正好说明 2.5 那个
> 日期格式问题有多容易复发。

**② 读取方：5 个数据集只有下载器、没有消费方**（B12）

`margin` / `northbound` / `futures` / `options` / `etf` —— 只在
`run_download.py` 的注册表和下载器里出现，没有任何分析或回测代码读它们。
占用不大，风险是"以为有数据在用"。

**③ 列一致性：发现一处真冲突、两处已知分裂**

新增 `--check schema` 里的**逐列存在性**与**全库列一致性**检查（见下），
查出 3 处列集分裂，其中 2 处是设计使然（已声明），1 处是真问题：

| 数据集 | 分裂 | 性质 |
|---|---|---|
| `frozen/financial` | `balance_`(155列) / `profit_`(88) / `cashflow_`(100) | ✅ 设计使然（三张报表） |
| `frozen/industry` | `stock_industry`(5) / `sw_l1`(8) | ✅ 两张不同的表，`loader.py` 按文件名区分 |
| `frozen/stocks` | `all`(9) / `data`(4) | ✅ 新旧两种产物，读取方按文件名区分 |
| **`frozen/valuation`** | 本应是**一种** | 🔴 **差点被 `ValuationDownloader` 打破**（B16） |

**B16 详情：一个还没引爆的哑弹**

`database/downloader/valuation.py` 早期版本做两件与数据集约定相反的事：
把 `total_mv/circ_mv` **除以 1e4（万元→亿元）**、把列名 **`turnover_rate`
改成 `turnover`**。而它写的是**同一个** `frozen/valuation`
（`save_year(..., force=True)` 会覆盖已有文件）。

后果：一旦有人跑 `python scripts/run_download.py --redownload valuation`
（该命令就写在脚本自己的 docstring 里），那个股票的文件就变成
"亿元 + turnover" 口径 —— `factors/panel.py` 取 `turnover_rate` 会全空，
`total_mv` 缩小 1 万倍，而**市值因子、行业中性化、组合权重全部用它**。
这是配置注释里点名的"双重复权"同类事故。

**当前数据未被污染**（抽样 400 文件 + 全库中位数：71,952 文件全部
`turnover_rate`、中位市值 509,971 万元 ≈ 51 亿元）。已修：
- 去掉换算与改名，严格保持 tushare 原样（万元 / `turnover_rate`）
- `_from_baidu` 回退路径同样修了两处：akshare 的总市值是**亿元** → ×1e4；
  且它只给 3 个字段，**必须把缺的列补成 NaN**，否则那些文件列不一致，
  任何 `read_parquet(glob)` 选到缺列都会抛 `schema mismatch`

**④ 门禁补强（本轮新增的三条，都是"能提前发现上面这类问题"的）**

1. **逐列存在性**：`count(*)` 不引用任何列，所以**缺列的文件不会让查询失败**。
   改为对 `required` 里每一列单独 `SELECT count(列)` —— 缺列立刻抛错。
2. **单位中位数下界**：原来的 `units` 只设上界，而"亿元污染"的数值**更小**，
   照样落在 `[0, 1e11]` 内。给 `total_mv` 加中位数下界 1e4 万元 ——
   正常中位数 5e5，被换算过会掉到 ~50，差 4 个数量级。
3. **全库列一致性**：逐数据集比对文件间的**列名集合**（不比类型 ——
   `financial`/`dividend` 逐文件 INTEGER/DOUBLE 不同是正常的）。
   带**声明式白名单**，只放过上表里那 3 处已声明的分裂；
   任何**新的**未声明分裂都会失败。

**⑤ 其他清理**

- `db/_MANIFEST.json`（B13）：原先手写、无生成方无读取方，内容已与
  `config.RECIPES` 漂移（规则少了三条、`producer` 不一致）。改为
  `config.write_manifest()` 生成，`setup_database()` 每次重建。
- `database/query.py`（B14）：零调用方，且自建连接绕过 `connect_duckdb()`
  （进度条刷 stderr）、`create_views()` 用全目录递归 glob 会在
  `stocks`/`industry` 上抛 schema mismatch 并用 `except Exception: continue`
  吞掉。已就地标注"无调用方 + 三条不要用的理由"。
- `joinquant/data.py::_load_calendar`（B14）：零调用方（`trade_days()` 已改用
  面板日期），已标注。

  1,313,872 行做 A/B，`limit_up`/`limit_down` 完全相同，含 limit 为空的

#### B4 · 断点"按股票记" → 检测 + 补救 + 预防

**它已经真实发生过**，只是不在行情数据上：`frozen/etf`/`frozen/options`
的断点里各有 84 个日期（其中 43 个是交易日），**磁盘上只有 7 天**有数据 ——
36 个交易日被标成完成却永远补不回来。而 `daily_raw`/`adjust`/`valuation`
经逐 code 年份比对**没有截断**（这与上一轮的结论一致）。

三件事：

1. **预防**：`Storage.mark_done(key, span=(a,b), empty=False)` —— 记录本次
   **实际写出的数据范围**；`empty=True` 表示"已确认该 key 没有数据"，
   与"有数据但没记范围"区分开。各下载器的 `mark_done` 全部改成这两种语义。
   `download_frozen_tushare.py` 里那套自己的 `load_ckpt/save_ckpt` **已删除**
   —— 它非原子写、且会把 `Storage` 记的 `spans` 整个抹掉（两套实现写同一个文件）。
2. **检测**：`--check checkpoint`
   - 逐数据集：断点说完成、磁盘上却没有 → 按**可证伪性**分四类：
     ① **日期键**没有文件 = 确证问题（一个交易日拿不到数据永远不是"本来就没有"）
     ② 北交所 `920xxx` = C1 上游垃圾，不计
     ③ 股票键 + 断点**记过范围**却没文件 = 确证问题（断点在撒谎）
     ④ 股票键 + 旧断点（没记范围）= **无法判定**，列为信息（`--strict-checkpoint` 可当问题）
   - 逐 code 年份覆盖 vs `daily_raw`（参考真值）：抓"半路返回一截"的静默截断。
     `920xxx` 在 2023 年前的数据本身是垃圾（C1），排除。
3. **补救**：`--repair-checkpoint` 把确证缺失的 key 从断点摘掉，让下次下载重试
   （已对 etf/options 执行，168 条）；`--backfill-checkpoint` 用磁盘上的真实范围
   **回填旧断点**，让那批"无法判定"变成可判定（本次回填 28,997 条）。

实测结果：确证缺失 **168 条 = etf(84) + options(84)**，正是上面那个 bug；
其余 1,534 条"无法判定"、1,360 条 C1。修复后 `--check checkpoint` 确证一致。

> 执行环境备注：`holders`/`suspend`/`dividend` 的 `_checkpoint.json` 在本轮
> 沙箱里**写不进去**（WinError 5）—— 它们的 ACL 里缺沙箱身份的写权限，
> 而 `adjust`/`st` 有。这是沙箱环境问题，不是数据问题；你在正常 shell 里
> 重跑 `--check checkpoint --backfill-checkpoint` 即可补齐这三个。

### 2.12 补充消费方：`factors/market.py`（B12 闭环）

前面的数据审计反复出现同一个隐患：**"以为有数据在用"**。5 个数据集下好了、
修对了，但没有任何代码读它们。本轮把它们接成**市场级（时间序列）信号**，
用来调**总仓位**——与 `factors/panel.py` 的横截面选股面板分工明确。

| 数据集 | 接成的信号 | 说明 |
|---|---|---|
| `margin` | `margin_chg` | 两融余额 20 日变化率（杠杆资金进出） |
| `northbound` | `north_net` | 北向净流入 20 日均值（**仅 2025-05 起 300 行**） |
| `futures` + `index_daily` | `IF_basis`/`IC_basis`/`IM_basis` | 股指期货基差 =（期货收盘 − 现货指数）/ 现货 |
| `options` + `opt_basic` | `pcr_vol`/`pcr_oi` | 期权认沽/认购比 |
| `etf` | `load_etf_prices`/`load_etf_basic` | ETF 价格面板与基金基础信息 |

**PIT 是这里最要紧的一条**：两融、北向、期货结算、期权持仓**都是收盘后才发布**的，
当天拿不到。`market_signals(..., lag=1)` 默认把整表右移一个交易日；不做这一步
就是典型的"用今晚才知道的数决定今天怎么交易"。回归测试
`test_market_signals_lag_is_exactly_a_shift` 断言 `lag=1` **严格等于** `lag=0`
右移一行。

同样隐蔽的是**分位阈值的前视**：`exposure_from_signal` 用**扩张窗口**算分位
（第 t 天只用 `[起点, t]` 的数据），否则 2018 年的仓位会"知道"2025 年的分布。
测试用"截断未来数据后历史仓位必须逐点不变"来卡这一点，并用全样本分位作**反面对照**
（它必须变），确保这个测试真的测到了东西。

接入方式：`PortfolioBacktestEngine.run(panel, target_weights, exposure=expo)`。
`apply_exposure` 只在**调仓日**缩放目标权重——择时通过"这次调仓多买还是少买"生效，
调仓日之间不因信号变化临时加减仓（那会产生大量无谓交易，也把信号噪声当调仓理由）。

### 2.13 市场级信号到底有没有预测力（**结论：基本没有，不要接**）

新增 `scripts/market_signal_eval.py` 做诚实的预测力检验，门槛是
**全样本与样本内 |IC| ≥ 0.05、不重叠分块 |t| ≥ 2、样本内外同号**。
分块 t 值用它而不是朴素 t 值，是因为重叠窗口（未来 20 日收益、每天算一次 IC）
会让样本高度自相关、朴素 t 值虚高好几倍。

基准 000300.SH、2018-01-02 ~ 2026-09-16、未来 20 日收益：

| 信号 | 样本 | IC | 分块 t | IC(样本内) | IC(样本外) | 分层(低/中/高) |
|---|---|---|---|---|---|---|
| `margin_chg` | 2058 | −0.057 | −0.37 | −0.023 | −0.098 | +14.3% / +0.7% / −4.2% |
| `north_net` | 259 | −0.520 | — | — | −0.520 | +52.2% / +17.3% / −13.5% |
| `IF_basis` | 1978 | −0.135 | −2.03 | −0.031 | −0.280 | +12.5% / +3.3% / −0.8% |
| `IC_basis` | 1978 | −0.121 | −2.20 | **−0.051** | −0.216 | +13.9% / +2.6% / −1.4% |
| `IM_basis` | 973 | −0.139 | −0.30 | +0.710 | −0.236 | +12.9% / +0.6% / −0.3% |
| `pcr_vol` | 1591 | +0.009 | +1.37 | +0.056 | −0.043 | +2.6% / +0.9% / +7.8% |
| `pcr_oi` | 1591 | +0.028 | +0.59 | −0.001 | +0.045 | −1.7% / +4.6% / +8.6% |

**只有 `IC_basis` 过门槛，而且是擦线过**（样本内 |IC| = 0.051，刚过 0.05；
t = −2.20，刚过 2）。其余全部不合格：`margin_chg`/`pcr_*` 的 IC 接近 0；
`IF_basis` 样本内 |IC| 只有 0.031（全靠样本外撑）；`IM_basis` 样本内 **+0.710**、
样本外 **−0.236**，符号直接翻转，是典型的"某段时间的风格恰好如此"；
`north_net` 只有 259 个样本，无法判断。

分层看，四个基差信号都是**单调递减**的（基差越高、未来收益越低），方向与
"升水 = 看多"的先验**相反**——所以 `exposure_from_signal` 要按低基差加仓来用。
但 `margin_chg` 和 `pcr_*` 的分层不单调，`pcr_vol` 的样本内外符号还不一致。

**结论：不要把这些信号接进仓位管理。** 单信号都过不了门槛时，组合更可能是
拟合出来的；加进去只会增加参数与过拟合风险，不会提高收益。

> 本轮修的数据 bug 顺带说明了这件事有多重要：`margin` 的整行重复被修掉之后，
> `margin_chg` 的 IC 从 −0.020 变成 −0.057、分层从"否"变成严格递减。
> **数据错了，因子检验的结论就是错的**——而且是往"没信号"的方向错。

### 2.14 `frozen/margin` 整行重复：一个主键检查抓不到的 bug（B18）

**现象**：`load_margin` 算出的融资余额中位数是 40,968 亿，而 2023-24 年 A 股
真实融资余额约 1.5 万亿——**偏高 2.5 倍**。

**根因**：`database/downloader/other.py::MarginDownloader.download()` 按季度拉数：

```python
for m_start in ("0101", "0401", "0701", "1001"):
    self._tc.call("margin", start_date=q, end_date=f"{q[:4]}1231")   # ← 年末！
```

季度起点配的是**年末**，于是 Q1 拉 1~12 月、Q2 拉 4~12 月、Q3 拉 7~12 月、
Q4 拉 10~12 月——10 月以后的数据被拉了 4 遍。`pd.concat` 之后**没有去重**，
整行重复原样写进 parquet。实测各季度平均重复份数（2023 年）：

| 季度 | Q1 | Q2 | Q3 | Q4 |
|---|---|---|---|---|
| 平均重复份数 | ×1 | ×2 | ×3 | ×4 |

（Q1 略低于 1 是因为年初还没有北交所记录。2023 年文件 1,803 行，去重后 726 行
= 242 交易日 × 3 交易所，完全吻合。）

**为什么以前查不出来**：这个数据集的主键是 `(trade_date, exchange_id)`，
**每个主键仍然唯一**（重复行之间也一样），所以任何主键唯一性检查都是绿的。
只有"整行完全一致"才能发现。

**修复**（三层）：
1. **下载器**：季度区间闭合到季末（抽成可测的 `quarter_ranges()`），并在
   `concat` 后加 `drop_duplicates()` 作二次防线。
2. **数据**：`--check duplicates --repair-duplicates` 就地去掉 18 个文件里的
   13,396 行重复（原子写回）。去掉的是"API 从未返回过、纯由区间重叠造出来的
   副本"，属于**还原**而非篡改原始数据。
3. **门禁**：新增 `--check duplicates`，逐文件比对 `count(*)` 与
   `count(DISTINCT *)`，已纳入 `--check all`。
   覆盖策略按实测耗时设计：**批量数据集全扫**（margin 17 个文件、etf/options
   各 1,627 个日期文件…合计约 13 秒），**按代码数据集抽样**（daily_raw/
   valuation/adjust 各 7 万余个，逐个扫不现实；跨年均匀抽 25 个——系统性缺陷
   每个文件都会中招，抽就必中）。另加回归测试两条：`quarter_ranges` 区间不重叠、
   以及 frozen 数据无整行重复。

> 验证：修复后 2023-06-01 三市合计 = 15,196 亿（与真实值一致），每个交易日
> 恰好 3 行，`--check duplicates` 全绿。
>
> 顺带发现的两个小问题：`dividend/603707.parquet` 有 1 行重复（已一并去掉）；
> `margin` 各年分区 schema 并不完全一致（`rqyl` 在 2010-2017 是 INTEGER、
> 2018+ 是 DOUBLE，DuckDB 在普通查询里会自动提升，只有 `DISTINCT *` 会踩到）
> —— 这一点写进了回归测试的注释，因为**第一版哨兵测试就是因为整库
> `DISTINCT *` 抛异常被 `except: continue` 静默跳过，却仍然打印 OK**，
> 等于没测它唯一要保护的数据集。

**现象**：`python scripts/daily_update.py` 跑完 1.5 小时的下载后，在"重建清洗层"
阶段崩溃：

```
pyarrow.lib.ArrowInvalid: Could not open Parquet input source '<Buffer>':
Parquet magic bytes not found in footer.
```

**根因**：`daily_update.py::upsert` 直接写最终路径 ——

```python
merged.to_parquet(path, index=False)      # ← 非原子写
```

写一半被中断（磁盘/进程/断电）就留下**半截文件**。实测那个文件是
`frozen/daily_raw/year=2026/601089.parquet`，**1,570 字节，头部魔数 `PAR1`
还在、尾部变成了零字节**。

这个 bug 之所以能潜伏很久才爆，是因为**每一层都在帮它隐瞒**：

| 环节 | 行为 | 后果 |
|---|---|---|
| 写入 | 非原子写 | 留下半截文件 |
| 下次更新读取它 | `except Exception` 吞掉，只打印一行 `{code} 失败: ...` | 混在 5,556 只的进度条里**根本看不见** |
| 重建清洗层 | 没有 try/except，直接抛到顶层 | 整个任务挂掉 |

**最危险的是"就地覆盖"**：`rebuild_cleaned_year` 是边读边覆盖，按文件名排序，
所以崩在 `601089` 时排在前面的股票已是新数据、后面的还是旧数据，而**目录里
文件数完全正常** —— 这种"半新半旧"的清洗层不报错就没人会发现，回测会静默
用到不一致的数据。

> 还有一个更隐蔽的陷阱差点踩进去：旧文件读不出来时，如果把"读不出来"当成
> "文件不存在"，就会走 `else` 分支只写 `new` —— 即把这次 **15 天**的窗口
> 当成全部历史写进去，这只股票**多年的数据被静默删除**，而且看起来完全正常。
> 这比留一个坏文件糟糕得多：坏文件至少会报错。所以 `upsert` 现在遇到损坏
> 分片是**拒绝写入 + 记录 + 报错**，绝不走"当作空文件"这条路。

**修复**：

1. **统一原子写**：新增 `database/storage.py::atomic_to_parquet`
   （写临时文件 → 用 `ParquetFile` 校验 footer → `os.replace`），
   `upsert` / `rebuild_cleaned_year` / `rebuild_limit_year` 全部改走它。
   校验失败时**最终文件不会被替换**，旧的好数据还在 —— 这是原子写相对
   "直接写最终路径"的核心价值，有专门的测试盯这一点。
2. **检测**：新增 `is_valid_parquet`（**头尾都查** —— 只看头会漏掉截断文件，
   这正是那些坏文件的形态）与 `find_corrupt_parquet`。
3. **门禁**：`--check parquet`，默认只查每个数据集最新一年（1~25 秒），
   全量要显式 `--parquet-all`。**跳过 `year=2005` 占位数据集** ——
   第一版把 `financial` 的 1.6 万个占位文件也算进"最新一年"，实测 201 秒，
   修掉后 1.2 秒。
4. **修复命令**：`--repair-corrupt` —— 把坏文件隔离到 `db/.corrupt/`
   （保留取证），然后对涉及的代码**重下整年**。为什么必须整年：分片是按
   `(代码, 年份)` 存的，文件坏了就等于这一年的历史没了；只补最近 15 天
   会把整年写成 15 天，**比坏文件更糟**（看起来是好的）。
5. **`--only rebuild`**：重建阶段崩溃后不必重跑 1.5 小时下载。
6. **重建阶段失败即回滚**：`rebuild_cleaned_year` 返回失败文件数，非零就
   立刻回滚清洗层，绝不把"半新半旧"的层留在磁盘上。

#### ① C6 · 冲击成本接进多因子 + 滑点默认不再是 0

`multifactor_backtest.py` 原先**连 `--impact-model` 参数都没有**，`--slippage`

验证。现在统一到其他脚本的口径（`fixed` + 1bp），并可用 `--impact-model sqrt`

同时修掉两处同类默认值：`joinquant/api.py` 的 `JQEngine` 硬编码
`FixedSlippage(0.0)`（两个 Clone 策略走的就是这条路）、

策略内显式调用 `set_slippage()` 时仍以策略为准（聚宽语义）。

#### ② 未来函数自检接进组合路径

先查清了一件事：**原有的"未来因子检测"基本是装饰性的**。
`scripts/backtest.py::auto_lookahead_report` 只检查了"成交日期在数据区间内"，
而 `check_lookahead` 若传入全量面板，会对除最后一个决策日外的**每一天**
都报违规（面板覆盖到回测结束），结论毫无意义。

本轮做了三件事：

1. **引擎层校验 `check_fill_timing`** —— 引擎不需要知道策略用了什么数据，
   但能保证"成交不早于决策"。这正是组合路径最容易踩的地方：决策日和成交日
   共用一个日期索引，"用当天收盘算权重、又按当天收盘成交"只需写错一行。
   `next_open`（默认）下同日成交直接判违规；`same_close` 不判违规但**显式声明
   为温和前视**，不再静默放过。
2. **堵住全量面板这个坑**：`assert_no_lookahead` 检测到像全量面板时直接报错，
   并告诉调用方该用 `check_fill_timing` 还是 `verify_point_in_time`。
   宁可报错，也不静默产出成千上万条假违规。
3. **`multi_engine.run(audit_lookahead=True)`** 默认开启，结果里带
   `lookahead_report` / `lookahead_violations`，违规时 `logger.error` 并在
   `summary()` 里显示。

> 引擎能保证的只有"成交不早于决策"。**策略实际用了哪些数据引擎无从得知** ——
> 那部分要由调用方用 `verify_point_in_time` 逐决策校验
> （`semiconductor_rotation.py` 是正确范例：记录每次决策实际使用的数据切片）。

#### ③ D2 · 组合层风控（新设计，不是"接根线"）

查清后发现问题比文档写的更严重，也更根本：

```python
# risk/manager.py —— 所有规则的签名都是这个
def check(self, signal: Signal, portfolio: Portfolio) -> Signal
```

`Signal` 是**单标的**概念（`Action.BUY/SELL/HOLD` + `size`）。这套东西接不进
组合引擎 —— 组合引擎收到的是一张权重宽表，没有"某一只股票的买卖信号"。
所以 D2 不是"忘了加一行调用"，而是**风控层是按单标的语义写的**。

新增 `risk/portfolio_rules.py`：

| 规则 | 行为 | 为什么这么设计 |
|---|---|---|
| `MaxDrawdownDeRisk` | 回撤超阈值时按**线性斜坡**压低总仓位 | 直接清仓会在阈值附近来回抖动，产生巨额无谓交易 |
| `MaxWeightRule` | 单票上限，超出部分**削掉不外扩** | 再分配会把权重推给第二大的那只，越控越集中；削掉 = 留现金，方向保守 |
| `MaxTurnoverRule` | 换手超上限时向现有持仓靠拢 | 纯降风险；无上期权重时**不触发**（不凭空假设持仓） |

两条硬约束：**风控只能降风险**（最后统一 clip，防"风控变杠杆"，有测试用
一条恶意放大 20 倍的规则验证兜底）；**触发要留痕**（`risk_events` 进结果和
报告 —— 否则事后看不出"这次减仓是策略决定的还是风控砍的"）。

接入 `PortfolioBacktestEngine.run(risk_manager=...)`，脚本侧
`--max-weight / --max-drawdown / --max-turnover`（默认全关 = 保持原行为）。

> ⚠️ 一个容易踩的坑：`PortfolioRiskManager` 有 `_prev_weights` 内部状态
> （换手规则要用）。同一个实例跨 训练集/测试集/全区间 复用会让状态串味 ——
> 测试集第一次调仓会拿训练集末尾的持仓当"上期持仓"。所以脚本里传的是
> **配置**，每段回测现建一个实例。

### 2.17 B7 解决：用 `index_member_all` 建 PIT 行业归属

**我之前的结论是错的。** 在 2.16 里我把 B7 登记成「需要额外数据、tushare 无此接口」——
那是只看了 `stock_basic.industry`（当前快照）就下的判断。实际上 tushare 有
**申万行业成分（分级）`index_member_all`**，直接输出 `in_date`（纳入日期）、
`out_date`（剔除日期）、`is_new`，正是构造 PIT 行业归属的原料。权限 2000 积分。

#### 这个接口有个和 `opt_daily` 同款的坑

直接 `pro.index_member_all()` 实测**正好返回 3000 行**、`is_new` 全是 `Y`、
`out_date` **100% 缺失**。A 股有 5,400+ 只，也就是说**默认调用是被截断的**，
而且一条历史记录都没拿到。必须用 `limit`/`offset` 翻页。

翻页后拿到的完整数据：

| 集合 | 行数 | 股票数 | `out_date` |
|---|---|---|---|
| `is_new='Y'` | 5,906 | 5,906 | 恒空（当前有效） |
| `is_new='N'` | 2,006 | 1,646 | 恒非空（已剔除） |

**1,646 只股票有 ≥2 段行业区间**（最多 6 段），`in_date` 零缺失。合计仅
**7,912 行、约 4 次 API 调用**。落盘 `frozen/industry/year=2005/sw_member.parquet`。

#### 空档处理：不能跳回当前快照

原始记录有空档。实测 `000007`：

```
家用电器 [1992-04-13, 2006-08-31]
房地产   [2006-09-01, 2009-05-27]
有色金属 [2013-07-01, 2014-06-30]     <- 中间空了 3 年多
社会服务 [2014-07-01, 2017-06-28]
综合     [2017-06-29, 2019-07-23]
商贸零售 [2019-07-24, 至今]
```

2009-05-28 ~ 2013-06-30 **没有任何记录**：`out_date` 只说"退出了房地产"，
没说"去了哪儿"。三种处理方式：

| 做法 | 评价 |
|---|---|
| 沿用上一段（房地产） | ✅ **本实现的选择** —— 标准 PIT 口径「未观测到变更 ⇒ 视为未变更」，也正是当时你数据库里真实能看到的东西 |
| 落到当前快照（商贸零售） | ❌ **明确的前视**：2010 年不可能知道它 2019 年会变成商贸零售 |
| 标成"未分类" | ⚠️ 信息丢失，这些股票会被抱团中性化 |

所以 `industry_intervals(carry_forward=True)` 把区间拼成**首尾相接、不重叠**
（每段结束 = 下一段 `in_date`），并对全部 5,906 只股票验证了这一点（有测试）。

#### 中性化的性能陷阱与正确性

`_neutralize_panel` 原来只接受 **时不变**的 `pd.Series`。改成支持 **PIT 的
`pd.DataFrame`**（index=日期, columns=代码）。

这里有个必须绕开的性能陷阱：朴素做法是"逐日 groupby"，而这个文件里**已经
踩过一次**（逐行 groupby + 带标签 setitem，11 因子 × 2596 行 = 2.8 万次操作，
实测 30 分钟跑不完）。所以实现是**按"行业配置快照"分块 + 块内沿用原来的
向量化实现** —— 块数 ≈ 行业变动次数（约 1,600），而不是日期数。

只有"变过行业"的股票参与快照指纹（5,906 只里 4,260 只从未变过），
指纹矩阵从 5,900 列降到约 1,600 列。

**正确性靠与"逐日手工分组去均值"逐元素对齐来保证**（有测试，含两次换行业的
边界）—— 分块边界只要错一天，就会用错行业的均值，而且不会报错。

另外 `neutralized_score` 的 `ind_map` 现在两种形态都收，若行业完全不变则走
快路径退化成静态分组（结果一致，有测试）。

### 2.18 C1 修正：改用证券主表三层过滤（推翻 2.16 的"保守排除"）

**2.16 里 C1 的修法是错的**，而且错得很隐蔽 —— 我当时说它"保守"，其实它
**换了个地方继续带前视**。

#### 错在哪

2.16 的做法是「把 `920xxx` 的涨跌停置 NaN + **按代码前缀**排除出股票池」。
问题不在"排除"，而在**排除的依据**：

| 旧依据 | 为什么错 |
|---|---|
| 代码前缀 | 前缀是**今天的编码约定**，不是"这只证券当时挂在哪个交易所"。转板股（新三板 -> 北交所/科创板）在前缀上完全看不出来 |
| 当前 `frozen/stocks` | 它只含**当前状态**，用它判断"当时是否可交易"本身就是前视 |
| `name.str.contains("退")` | `daily_update.live_codes()` 就是用它猜退市股：**既漏**（改名/重组/被吸收合并退市的不带"退"）**又错**（退市整理期带"退"但仍在交易） |

再加上**幸存者偏差**：如果股票池只从"当前存在的股票"里选，那些"当时存在、
后来退市"的股票整个不在池子里，历史组合表现会被系统性**高估**。

#### 证券主表缺的字段

查了 `frozen/stocks/all.parquet`，发现三层过滤所需的字段**一个都没存**：

| 需要的字段 | 2.16 时的状态 |
|---|---|
| `exchange` | ✗ 缺失 —— `StockListDownloader` 的 `fields` 里根本没请求 |
| `delist_date` | ✗ 缺失 —— 同上 |
| `list_status` | ✗ 缺失 —— L/D/P 三次调用 `concat` 时**没记状态**，落盘即永久丢失 |

原来的 `all.parquet` 只有 5,889 行 × 8 列。所以那时的"排除"只能靠名字猜。

#### 修法

1. **补全证券主表**：`StockListDownloader` 请求
   `exchange,list_date,delist_date` 并**手动打 `list_status` 标签**
   （接口不返回这一列，不打标就会在 concat 时丢失）。
   重下结果：**5,904 只** = 上市 5,565 + 退市 339 + 暂停 0；
   `exchange` = SZSE 3,088 / SSE 2,467 / **BSE 349**；339 只带真实 `delist_date`。

2. **新增 `database/master.py`**：实现三层过滤，全是**日期比较**，
   不含任何"今天叫什么/今天属于谁"：

   ```python
   pool_t = master[
       master['exchange'].isin(['SSE', 'SZSE'])                       # ①
       & (master['list_date'] <= t)                                   # ②
       & (master['delist_date'].isna() | (master['delist_date'] > t))  # ③
   ]
   ```

   - ① 用 `exchange` 而不是代码前缀 —— 直接从根上排除 NEEQ/BSE，C1 因此**不再是
     一个"要额外处理"的问题**；涨跌停置 NaN 保留为诚实标记。
   - ③ 边界**严格**：退市当日即不可交易（`delist_date > t`，不是 `>=`）。
     实测 `000005 ST星源(退)`：2024-04-25 可交易、**2024-04-26 退市日不可交易**。
   - 主表里查不到的代码一律 False —— 「不知道」不等于「可以交易」。

3. **接进 `universe/pool.py`**：`build_universe` 最前面加上主表过滤。
   以前这里只有 `close.notna()`，等于把"有没有行情"当成"该不该交易"，
   而交易所归属这一条它根本表达不了。股票池基础从 2,647 降到 **2,098**
   （剔掉 BSE 与不在交易期的标的）。

4. **`daily_update.live_codes()` 改用 `delist_date`**，不再用名字含"退"。
   结果 5,565 只，与主表判据**完全一致**。它**不按交易所过滤** ——
   数据要下全（含 BSE 344 只），进不进回测池由 `UniverseSpec.exchanges` 决定。

5. **缺字段时不静默放行**：`master_capabilities()` 探测主表能力，
   `build_universe` 在主表存在但缺 `exchange`/`delist_date` 时发
   `RuntimeWarning`（完全没有主表时不警告 —— 那是"没数据"而不是"数据坏了"）。

6. **顺带修正 `listed_days_panel`**：它原先数的是 `close.notna().cumsum()`，
   即"**面板里有几根 bar**"，而不是"上市后过了几个交易日"。一只 2005 年上市、
   但本地数据只从 2015 年起的股票，2016 年的 bar 数只有两百多，会被
   `min_listed_days` 误判成次新股。现在改用 `list_date` 在**全市场交易日历**
   上数交易日（实测 `000001` 到 2024-01-01 是 7,999 个交易日、`301001` 是 633）。

   > 这里我先写错过一次：用面板自身的 index 去 `searchsorted`，结果
   > "面板只有 30 天"时算出 1..30，跟上市多久毫无关系。**必须借全市场日历**，
   > 因为面板往往只覆盖回测区间。

   同时给 `build_universe` 加了 `master=` 注入参数：合成测试代码
   （`000001`~`000050`）**恰好都是真实股票代码**，不注入就会去查真实主表，
   结果依赖本机有没有 `db/`；而 CI 里没有主表，会被"查不到即不可交易"整池剔掉。

#### 为什么默认排除北交所

`exchanges=("SSE","SZSE")` 是默认值，两个现实原因：
① 其前身（新三板精选层）在 2021-11-15 开市前 `pre_close` 不可信（C1）；
② 流动性与主板差一个量级，容量分析会失真。
需要时显式传 `exchanges=("SSE","SZSE","BSE")` —— 是**可配置**的，不是写死。
`unreliable_limit_mask`（前缀判据）保留为第二道保险，只在显式纳入 BSE 时生效。

> 复盘：2.16 我把"用前缀排除"当成了保守做法，实际上它只是把前视从
> "涨跌停价"挪到了"池子成员资格"。**任何用当前状态决定历史行为的做法都是前视**，
> 不管它看起来多保守。正确的地基只有一种：时点正确的证券主表。

新增测试：`tests/test_security_master.py`（9 项）。

### 2.19 B10/B11/C2b/C4b 四条整改（含一条被数据推翻的前提）

#### C4b：原描述是错的，真实机制是「复牌首日不设涨跌幅」

文档（和 2.16 的登记）写「2006–2007 未股改 S 股无涨跌幅限制」。**用行情数据
反证后不成立**：

| | 行数 | \|涨跌幅\| > 10.5% | 占比 |
|---|---|---|---|
| 纯 S 股（2006-2007） | 68,552 | 97 | **0.14%** |
| 全市场同期 | 611,411 | 960 | **0.157%** |

**几乎一样** —— 纯 S 股照样受 ±10% 约束。若按原描述实现（给纯 S 股整个区间
放行），会**错误地取消约 6.8 万行的涨跌幅限制**。

真实机制是**停牌复牌首日不设涨跌幅**：960 行越界里能判定"距上一根 K 线间隔"的
771 行中，**770 行（99.87%）是复牌首日**；|涨跌幅| > 20% 的 444 行**全部**是。
逐案核过：

```
S石炼化 → 长江证券  2007-12-27  +310.10%   停牌数月，复牌当日改名
S京化二 → 国元证券  2007-10-30  +255.76%   同上
S华源发 → 华源发展  2007-04-25  +198.22%   同上
```
都是 `pre_close` 还停在停牌前最后收盘价，**次日立刻恢复 ±10%**
（600272 次日 −10.00%、000728 次日 +0.99%）。

**阈值用「错过的交易日数」而不是自然日**（后者会把春节/国庆长假算成停牌）：

| 错过交易日 | 行数 | 越界行 | 越界率 |
|---|---|---|---|
| 0 | 601,086 | 1 | 0.00% |
| 1-5 | 7,750 | 0 | **0.00%** ← 有限制 |
| 6-10 | 750 | 26 | 3.47% ← 混合带 |
| 11-20 | 987 | 480 | **48.63%** ← 明确无限制 |

取 11（证据最硬的区间）。**边界是经验性的，不是查到的交易所条文** ——
这是它仍留在缺陷表里的原因。

> ⚠️ 实现时踩了一个坑：复牌判定靠"相邻两根 K 线之间错过了几个交易日"，
> 所以传入**日期子集**时（比如只取月度调仓日、或测试里抽样的 3 个日期）
> 会把每个采样点都误判成复牌首日。`test_limit_rules` 立刻抓到了这个 bug。
> 现在 `resume_no_limit` **默认关闭**，只有确认输入是完整日线序列的
> 两个重建路径（`rebuild_limit.py`、`daily_update.rebuild_limit_year`）显式开启。

也顺带修正了 `RELISTED_CODES` 的维护方式：**记公司主体而不只记代码**
（重新上市通常换代码换名），并明确写死「**恢复上市**」名单（盐湖股份、
皇台酒业等，代码未变），防止有人把它们误加进重新上市排除名单 —— 那会制造
**新的误拦**。

#### B11：`suspend_timing` 的 schema 地雷 + 三层交叉验证

**先查出一个潜伏 bug**：`frozen/suspend` 的 `suspend_timing` 列在"全空值"的
文件里被 pyarrow 推断成 **NULL 类型**、有值时是 VARCHAR。两者混在一个目录里，
`read_parquet('year=2005/*.parquet')` 会按**第一个文件的 schema** 去读，
直接抛 `ConversionException: failed to cast column suspend_timing from
VARCHAR to NULL`。原先 4,417 个文件都处于这个状态，只是没人投影这一列所以
没暴露。

修法：读侧 `union_by_name = true`（`database/status.py`），写侧统一
cast 成 VARCHAR（`downloaders/meta.py`），防复发。

**然后用上了这个字段**——`suspend_timing` 非空 = **日内停牌**，与全天停牌
必须分开：日内停牌当天仍有可交易时段，整天禁掉会误伤。
全区间 522,306 条 S 记录里，日内停牌 2,603 条（0.498%），取值如 `09:38-09:49`。

**三层"不可成交"来源的交叉验证**（2020-2024）：

| | 条数 |
|---|---|
| `suspend_d` S 记录 | 13,963 |
| 其中**无 K 线**（全天停牌） | 13,269 |
| 其中**有 K 线**（日内停牌） | 694 |
| 矛盾（该无 K 线却有成交量） | **0** |

694 与日内停牌数**完全吻合** —— 三层模型自洽，`audit_coverage()` 已固化成检查。

#### B10：更正一处接口判断（`index_member` 不是中证指数）

2.16 写「`index_member`（含进出日期）无权限」。**实际是通的**，但它是
**申万行业成分**（返回 `801862.SI` 那套），`index_member_all` 是它的分级版。
所以准确的说法是：

> tushare **没有**提供中证指数带 `in_date`/`out_date` 的接口。

免费且精确的两条路（未实施，留给后续）：
1. 聚宽 `get_index_stocks(symbol, date)` 支持历史日期，按调整日批量导出；
2. 中证指数官网历次样本调整公告（Excel/PDF），沪深300/中证500/中证1000
   各约 40 次调整，一次性建设。

现状（月末快照 + 只取 `<= t`）方向是"晚了才纳入"，属可接受的降级；
建精确版后应做敏感性分析对比。

### 2.20 T1 开工：标准结果对象 + 集中渲染层（⑤ 完成）

**排序原则（第二轮）**：T0 解决"**算得对**"（静默错误），T1 解决"**算得全**"
（未建模的摩擦、近似、方法学缺陷必须**被量化或被声明**）。T1 次序按
"每一步为下一步铺路"排：

    ⑤ 标准结果对象 → ④ 风格分解接线 → ② fill-timing 统一
    → ① 埋点度量 → ③ 门禁通用化 → ① 排队建模

#### ⑤ 做完了什么

**病根**：每个脚本各自 print 报告 → **接 N 次、漏 N-1 次**。

| 项 | 整改前接上的脚本 |
|---|---|
| 已知缺陷附注 | 只有 `multifactor_backtest.py` |
| 前视自检 | 引擎会算，只有部分脚本打印 |
| 风控触发 | 引擎会记，**没有**脚本打印 |

**改法（两件）**：

1. **缺陷从"手工挂"升级为"自动匹配"**
   `KnownDefect` 增加 `trigger(ctx) -> bool`，新增 `match_defects(ctx)`。
   渲染层按**回测输入**自动判断本次是否触及：

   | 回测输入 | 自动报出 |
   |---|---|
   | 用**当前快照**行业归属 | **B7**（前视） |
   | 用 PIT 行业面板 | 不报 B7 |
   | 用了指数成分 | **B10**（月末快照滞后） |
   | 池子含北交所/新三板 | **C1** |
   | 池子含重新上市股 | **C2b** |
   | 区间 ≥ 1 年 | B11 / C4b |
   | 短区间 | **无**（不产噪声） |

   两条设计约束：**没有 `trigger` 的条目不会被匹配**（宁可漏标，不误标一片
   噪声让人对附注麻木）；`trigger` 自身抛异常时记为**命中**而非静默忽略。

2. **新增 `analytics/result_report.py` 渲染层**，报告结构固定为：
   头部声明（**口径 + 门禁状态 + 缺陷计数，放在所有数字之前**）→ 绩效 →
   已知缺陷附注 → 前视自检 → 风控触发 → 被制度约束拦下的委托。

   `MultiBacktestResult` 相应增加 `defects` / `context` / `fill_timing` / `gate`
   四个字段与 `render()` 方法 —— 这就是 T1 后续几项（②③④）的**载体**：
   新脚本只要走标准对象就自动带全部附注。

**头部口径声明写死**（不允许调用方改）：

```
next_open  （T日收盘决策 → T+1开盘成交）：**可实现口径，主结果**
same_close （当日收盘决策且按当日收盘成交）：**上界，实盘不可复现**，只能作对照
```
没跑门禁时必须显式打印"**未执行**"，不能留空让人以为是干净的。

#### 顺带修的一个口径不一致

`multifactor_backtest.py` 的 `res.render()` 原本取引擎在**整个窗口（含预热期）**
算的指标，而脚本其它地方报的是**评估窗口**的指标 —— 两处数字会不一致。
现在 `run_one` 把结果对象的 `equity`/`metrics` 换成截掉预热期的那份再渲染。

#### 新增 `docs/日线局限与分钟级扩展痛点.md`

按项目定位（**日线研究平台**）记录 5 条"因为只有日线才存在"的痛点
（P1 封板成交 / P2 成交时点 / P3 日内停牌 / P4 复牌免限阈值 / P5 执行摩擦），
每条写清：**日线下能做到什么 → 天花板在哪 → 扩展需要什么**。
**不在那里设计方案，也不为它改动现有架构。**

一句话原则：**不要为了"更准"在日线上堆越来越复杂的近似** —— 那会把
"已知的近似"变成"未知的拟合"。日线平台的可信度来自**误差被标注清楚**，
不是来自误差被消灭。

新增测试：`tests/test_result_report.py`（7 项）。
