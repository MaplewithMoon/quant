### 2.1 数据层专项实测（2026-09）

**B2 到底错在哪 —— 比报告里写的严重**

| 位置 | ST 5% | 北交所 30% | 用什么当昨收 |
|---|---|---|---|
| `database/downloader/meta.py` | 有 | **无** | **`close.shift(1)`** ✗ |
| `scripts/daily_update.py` | 无 | 只认 `920` | **`close.shift(1)`** ✗ |
| `scripts/rebuild_limit.py` | 有 | `920/43/83/87/88` | 官方 `pre_close` ✓ |

`close.shift(1)` 是**未除权的上一日收盘** —— 10 送 10 的情况下算出的涨跌停价会差一倍。
而增量更新 `daily_update.py` 会拿它去**覆盖** `rebuild_limit.py` 生成的正确数据。

**量化影响**：现有 `cleaned/limit_price` 的 1,596 万行里，有 **1,152,719 行（7.2%）**
是错的 —— 创业板在 2020-08-24 之前被按 ±20% 计算，实际应是 ±10%。
方向上**让回测偏乐观**：涨停价偏高 → 少拦买入；跌停价偏低 → 少拦卖出。

**修复内容**（`database/limit_rules.py`，唯一实现）：
1. 三处调用方统一转调它，并加测试断言"不再各自实现、不再用 `close.shift(1)`"
2. 补上 **创业板 2020-08-24 注册制改革前 ±10%**（三套实现都没有）
3. 北交所统一为 `920/43/83/87/88`
4. 一律用**官方 `pre_close`**；缺这一列时**直接报错**，绝不退化成 `close.shift(1)`

**B4 的实测结论（已用证据化判据复验）**：仍在上市的 5,570 只股票中，
整年缺口共 **44 段，全部有"交易断裂"或"停牌记录覆盖"证据，0 段疑似数据缺失**。

判据（写进 `validate_data --check completeness`，不再是拍一个阈值）：
- **证据一 · 价格断裂**：缺口前一年在 12 月前就停止交易，或缺口后一年到 1 月后才恢复
- **证据二 · 停牌覆盖**：缺口年份 ≥80% 的交易日有 `suspend_type='S'` 记录

两条互补，缺一不可：`000757`（方向光电）2007-04 停牌、2013-02 才复牌，
整整 5 年没有日线，但 **`frozen/suspend` 里 0 条记录**（`suspend_d` 不记录
"暂停上市"）；而 `002015` 的 2015 年整年停牌（复牌首日 7.55 元跳空）
只能靠停牌记录解释。

**结论**：`mark_done` 粒度为"股票"确实是风险，但**没有造成实际数据缺失**。


**新增四条永久门禁**（`validate_data.py`）：

```bash
python scripts/validate_data.py --check limit         # 涨跌停规则一致性（逐行重算比对）
python scripts/validate_data.py --check completeness  # 年份完整性 + cleaned/frozen 一致性
python scripts/validate_data.py --check status        # 停牌/ST/涨跌停三张面板**非空**

```

### 2.2 停牌数据曾经完全失效（本次发现，已修）

`backtest/panel_data.py::load_status_panels` 里有两个叠加的错误，**都被
`except Exception: sus = pd.DataFrame()` 吞掉**，所以从来没有报错：

1. `frozen/suspend` 是**非年度数据集**（只有占位分区 `year=2005`），
   代码按回测区间拼 `year=2024/*.parquet` → 路径不存在 →
   DuckDB 抛 `IOException`。
2. `suspend.trade_date` 是 **VARCHAR `'YYYYMMDD'`**，不是 DATE。

**后果**：`suspended` 面板恒为空表 → `MarketRules(block_suspended=True)` 拿到
全 False → **停牌股照常买卖**，T+1 与流动性假设被架空。
实测 2024 上半年就有 **1,330 个停牌标记**（192 只股票）被漏掉。

**同时发现同一件事被实现了四遍，口径各不相同**：

| 位置 | 只取 `S` 停牌记录 | 日期处理 | 分区 glob |
|---|---|---|---|
| `backtest/panel_data.py` | — | 当成 DATE ✗ | 按年份区间 ✗ |
| `universe/pool.py` | ✗ 把 `R`(复牌日) 也算停牌 | ✓ | `year=*` ✓ |
| `database/loader.py` | ✗ 把 `R` 也算停牌 | ✓ | `year=*` ✓ |
| `joinquant/data.py` | 依赖上面的 panel | — | — |

`R` 是**复牌日，当天恢复交易**，把它当停牌会在复牌当天错误地禁止买卖。
实测全库 `R` 记录 **24,646 条（占停牌记录 4.51%）**，涉及 3,398 只股票；
其中只有 133 个 (股票, 日) 组合同时存在 `S`，也就是说约
**2.45 万个 (股票, 日) 组合被错误地判定为"停牌不可交易"**。

**修法**：新建 `database/status.py` 作为唯一实现，三处调用方全部转发过去；
`database/config.py` 新增 `year_globs()` 统一分区解析（只列真实存在的分区，
静态数据集忽略区间，数据集起始年份晚于区间起点时也不会拼出死路径）。
`limit_rules.st_mask` 同时接受 `Series` 与 `DatetimeIndex`，`st_panel`
也改为复用唯一的 ST 区间实现（此前是第三份，且失败时静默返回全 False）。
`load_st_intervals` 加缓存并改用 DuckDB 一次扫描（22.8 秒 → 1.75 秒）。

**影响面：不是所有消费方都受影响 —— 这点必须讲清楚，否则会误判成"修复无效"**

| 消费方 | 停牌面板缺失时的行为 | 是否被这个 bug 影响 |
|---|---|---|
| 聚宽移植层 `joinquant/data.py::paused` | 有**兜底**："当日无价格行即视为停牌" | **否**（重跑 v1/v2 结果逐位相同：+121.27% / +257.42%） |
| 组合/多标的引擎 `backtest/multi_engine.py` | `_bar()` 缺字段就跳过检查 | **是**（停牌股完全不受约束） |
| 股票池 `universe/pool.py` | 自己实现过一遍，能读到数据 | 部分是（`R` 复牌日被误判为停牌） |

所以"重跑聚宽策略结果不变"**不能**证明 bug 不存在 —— 它只是被兜底掩盖了。
真正的受害者是组合引擎那条路径。`validate_data --check status` 现在会
直接断言三张面板非空，无论哪个消费方、有没有兜底。

### 2.3 舍入方式：银行家舍入 vs 交易所四舍五入（本次发现，已修）

交易所口径是**四舍五入到分**，而 `round()` / `np.round()` 是**银行家舍入**
（round-half-to-even，恰好 .5 时向偶数靠）。浮点表示还会让结果"看运气"：
`10.05×1.1` 的浮点值略大于 11.055，`round()` 恰好给了对的 11.06；
换成 `11.05×1.1=12.155`（浮点略小）就错成 12.15。

**实测旧 `cleaned/limit_price`：涨停价 2.7%、跌停价 4.4% 的行与交易所口径差 1 分钱**
（1500 万行里约 50 万行）。

**修法**：`database/limit_rules.py` 改为**整数分运算**
（`(pc_cents × K + 5000) // 10000`），与浮点无关。
已核实全库 1,596.8 万行 `pre_close` **全部**落在 0.01 网格上（0 例外），
该前提由 `validate_data --check limit` 永久把关。

**重建后的前后比对**（新旧实现同时重算 15,967,594 行）：

| 变化来源 | 行数 | 占比 |
|---|---|---|
| 创业板 2020-08-24 前 ±10% | 1,152,824 | 7.22% |
| 取整改为四舍五入 | 879,695 | 5.51% |
| **合计有变化** | **2,032,519** | **12.73%** |

重建后**逐行重算 137.6 万行（抽样 300 只）与唯一规则完全一致**，
真倒挂 0 行。顺带发现两个"看似异常其实正确"的情形，已写进判据避免误报：
`limit_up == limit_down` 的 11 行全部是 **≤0.09 元股票的粒度塌缩**
（0.09 元的 ST 股 ±5% 上下限都四舍五入到 0.09）；238 个空值**全部是
`920xxx` 且全在 2023 年之前**（北交所 2021-11 才成立，此前是新三板历史，
`pre_close` 本就是垃圾值 —— 即 C1）。

### 2.4 派生缓存会静默返回旧数据（D5，已修）

`.cache/panel/<start>_<end>/` 原先**只以区间为键**。数据被重建后缓存仍然命中，
回测拿着旧数据算出结论 —— 而这一轮刚好改写了 115 万行涨跌停价，
**不修的话重跑也发现不了**。

**修法**：`database/provenance.py` 新增 `dataset_fingerprint()`，
缓存元数据记录所依赖 5 个数据集（daily / valuation / adjust / limit / suspend）
的「文件数 + 最新 mtime」；任一项变化即作废重载，**没有指纹字段的历史缓存一律作废**。
指纹扫描用 `os.scandir`（0.25 秒，`Path.glob` 要 7 秒，快 28 倍）。

### 2.5 tushare 日期字符串混格式导致静默丢数据（本次发现，已修）

全库审计（新增 `validate_data.py --check dates`）发现日期列**列类型不统一**：

| 类型 | 数据集 |
|---|---|
| `TIMESTAMP` | daily_raw / adjust / valuation / limit_price / index_daily / st.start_date … |
| `VARCHAR` | suspend.trade_date、index_cons.trade_date、dividend.*、financial.ann_date、holders.ann_date、st.end_date … |

更隐蔽的是 **VARCHAR 列内部还混着两种格式**：

```
'20230428'             绝大多数
'2025-06-03 16:01:59'  少数（tushare 自身返回不一致）
```

读取方写 `pd.to_datetime(s, format="%Y%m%d", errors="coerce")` 时，
第二种会**静默变 NaT**，紧接着被 `dropna()` 丢掉 —— 数据无声消失。
实测 `frozen/holders.ann_date` **548,603 行里有 8,152 行（1.49%）** 是这种格式。

另有一个 pandas 陷阱：`pd.to_datetime(series)` **不带 format** 时会
**按第一个元素定格式**，同一批里混两种格式照样漏（`'2025-06-03 16:01:59'`
在前时，后面的 `'2024-01-02'` 会被判成 NaT）。必须用 `format="mixed"`。

**修法**：新建 `database/dates.py::parse_tushare_date()`，
`factors/fundamental.py`（2 处：financial、holders）与 `joinquant/data.py`
全部改走它。检查项也从"必须是 YYYYMMDD"改成"**必须能被解析**"，
混合格式只作提示、不算失败。

| | 样本外回撤 | −31.59% | −31.68% | −0.09pp |

**怎么解读（重要，避免两个方向的误读）**

1. **不能**说"改了 12.73% 的数据却没影响，所以不重要"。这些策略是**月度调仓、
   低换手**，而涨跌停拦截用 `LIMIT_TOL` 容差判定"封板"，1 分钱的价格差

2. **也不能**说"聚宽策略结果没变 = 停牌 bug 不存在"。聚宽移植层有兜底
   （"当日无价格行即视为停牌"）掩盖了空面板；**组合引擎没有兜底**
   （`_bar()` 缺字段就跳过检查），它才是受害者 —— 规则组合少掉的 2 笔成交
   正是这条路径上的差异。
3. 真正该担心的是**未来**：一旦做高换手、做 2017–2020 的创业板、或把
   `block_limit_up_buy` 的容差调紧，那 203 万行的错误就会直接体现在收益上。
   现在这个隐患被永久门禁（`--check limit` 逐行重算）挡住了。

### 2.7 上市初期规则（C2）：实现 + 用行情数据反证

原来只按板块常规档位算，次新股上市初期的合法大涨会被当成"封板"而**多拦买入**。

**规则表**（`database/limit_rules.py::LISTING_REGIMES`，按"板块 × 上市日"选制度）

| 板块 | 期间 | 规则 |
|---|---|---|
| 主板 | ~2013-12-12 | 首日**不设涨跌幅** |
| 主板 | 2013-12-13 ~ 2023-04-09 | 首日 ×1.44 / ×0.64（基准=**发行价**） |
| 主板 | 2023-04-10 ~ | 前 5 个交易日**不设涨跌幅** |
| 创业板 | 2009-10-30 ~ 2020-08-21 | 首日不设涨跌幅 |
| 创业板 | 2020-08-24 ~ | 前 5 个交易日不设涨跌幅 |
| 科创板 | 2019-07-22 ~ | 前 5 个交易日不设涨跌幅 |
| 北交所 | 2020-07-27 ~ | 首日不设涨跌幅 |

**实现要点**

- "不设涨跌幅" → `limit_up`/`limit_down` 置 **NaN**。`MarketRules._num()` 对
  NaN 返回 `None` 会**跳过**涨跌停检查，正是"无限制"的语义（已在
  `market_rules.py` 就地写明，避免后人误以为是缺数据）。
- 首日 ±44% 的基准是**发行价**，而 tushare 首日的 `pre_close` 正是发行价 ——
  已实测确认（`002973 侨银股份` pre_close=5.74、high/pre_close−1=+44.08%）。
- ⚠️ ±44% **不是对称的**：上是 +44%、下是 −36%（×1.44 / ×0.64）。
- `daily_update.py` / `downloader/meta.py` 原先有
  `.dropna(subset=["limit_up","limit_down"])`，会把"不设涨跌幅"的行也删掉 ——
  已移除，否则增量更新会与全量重建口径不一致。
- 窗口按**市场交易日**计（`trading_calendar()`），停牌不顺延。

**用真实行情反证**（新增 `validate_data.py --check listing`）

| 情形 | 观测 | 结论 |
|---|---|---|
| 主板 2014–2023 首日 | 1,172 行中 **1,150 行**涨幅落在 [42%, 44.5%]，p50=+44.00% | ±44% 确实封顶 ✓ |
| 主板 2005–2013 首日 | p95=+175%、max=+742% | 确实无限制 ✓ |
| 主板 2024+ 首日 | 80 行中 78 行 > 44%，p50=+211% | 确实无限制 ✓ |
| 科创板前 5 日 | 3,089 行中 634 行 > 20% | 确实无限制 ✓ |
| 创业板 2020-08-24 后 | 3,035 行中 682 行 > 20% | 确实无限制 ✓ |
| 北交所首日 | 340 行中 99 行 > 30%，max=+1667% | 确实无限制 ✓ |

**已知残留（见 C2b）**：3 只**重新上市**股（国机重装 +188.9%、汇绿生态
+122.5%、新城控股 +235.9%）被误套首日 ±44%；另有 6 只 2014-01 上市的主板股
首日最高价落在 +45.2%（比 44% 高 1.1%，具体机制未查明）。

### 2.8 顺带查出的两个真规则错误（都由新门禁抓到）

加 `--check listing` 的"价格不得越过涨跌停"这条**实证**校验后，立刻红了
8,488 行 —— 追下去是两个独立的规则错误，而且都是**老错误**、之前所有校验
都没发现：

**① ST 的 ±5% 被错误地套到了创业板/科创板**

2020-08-24 创业板注册制改革后，**创业板与科创板的"风险警示股票"不再单独
设 5%**，仍按板块的 ±20%；北交所同理。早期 `limit_pct` 给所有 ST 一律 5%，
让这些股票的涨停价**偏低一半以上**。
实测：创业板/科创板越界 5,475 行，`limit_up/pre_close−1` 全部 ≈ 0.05。

**② 主板 ST 的档位在 2026-07-06 从 ±5% 放宽到 ±10%**

这个日期是**从行情数据反推**出来的，不是抄公告：

| 期间 | 主板 ST 股每日 \|pct_chg\| 上限 | 超 5.5% 的行数 |
|---|---|---|
| 2015–2025 全年 | 5.17~5.19% | **0** |
| 2026-06-22 ~ 2026-07-03 | 5.11~5.19% | 0 |
| **2026-07-06 起** | **10.08~10.26%** | 639（134 只股票） |

断点非常干净，因此按制度变更处理（`MAIN_ST_10PCT_FROM`）。同日价格越界
行数从 720 降到 0。**若日后拿到正式公告，核对/修正这一个常量即可。**

**修正后的越界情况**（`--check listing`）

| 指标 | 修正前 | 修正后 |
|---|---|---|
| 最高价 > 涨停价 | 8,488 行 | **302 行（0.0019%）** |
| 最低价 < 跌停价 | 7,527 行 | **1,205 行（0.0075%）** |

残留集中在 **2006–2007**（当年股权分置改革期间的未股改股 S 股**没有涨跌幅
限制**，规则表未建模）与零星的历史个案。门禁改为**比率判据 + 年份归因**
（阈值 0.02%），既能抓住新的系统性错误，又不会因为已知的历史个案永久变红。

### 2.10 全库数据审计（2026-09 第二轮）

对每个数据集做了**新鲜度 + 读取方 + 列一致性**三方面的体检，结论如下。

**① 新鲜度：整体健康，两处小缺口**

| 数据集 | 覆盖 | 状态 |
|---|---|---|
| daily_raw / valuation / adjust / daily_basic / limit_price | ~2026-08-28 | ok |
| financial / holders（`ann_date`） | 2026-08-28 | ok |
| fund_daily / index_daily | 2026-09-15 | ok |
| **etf / options** | 月度快照止于 2026-07-01 | ⚠ **缺 2026-08**（落后 77 天） |
| **northbound** | 仅 2025-05-27 起 | ⚠ 历史未下载 |

> 审计脚本第一版把 `holders` 误报成"落后 411 天"，原因是用了
> `try_cast(ann_date AS TIMESTAMP)` —— `ann_date` 是 VARCHAR `'YYYYMMDD'`，
> 转换全为 NULL，只剩那 8,152 行 ISO 格式的能显示出来。**审计工具自己踩了
> 同一个坑**，改用 `try_strptime` + ISO 兜底后才对。这正好说明 2.5 那个
> 日期格式问题有多容易复发。

**② 读取方：5 个数据集只有下载器、没有消费方**（B12）

`margin` / `northbound` / `futures` / `options` / `etf` —— 只在
`run_download.py` 的注册表和下载器里出现，没有任何分析或回测代码读它们。
占用不大，风险是"以为有数据在用"。

**③ 列一致性：发现一处真冲突、两处已知分裂**

新增 `--check schema` 里的**逐列存在性**与**全库列一致性**检查（见下），
查出 3 处列集分裂，其中 2 处是设计使然（已声明），1 处是真问题：

| 数据集 | 分裂 | 性质 |
|---|---|---|
| `frozen/financial` | `balance_`(155列) / `profit_`(88) / `cashflow_`(100) | ✅ 设计使然（三张报表） |
| `frozen/industry` | `stock_industry`(5) / `sw_l1`(8) | ✅ 两张不同的表，`loader.py` 按文件名区分 |
| `frozen/stocks` | `all`(9) / `data`(4) | ✅ 新旧两种产物，读取方按文件名区分 |
| **`frozen/valuation`** | 本应是**一种** | 🔴 **差点被 `ValuationDownloader` 打破**（B16） |

**B16 详情：一个还没引爆的哑弹**

`database/downloader/valuation.py` 早期版本做两件与数据集约定相反的事：
把 `total_mv/circ_mv` **除以 1e4（万元→亿元）**、把列名 **`turnover_rate`
改成 `turnover`**。而它写的是**同一个** `frozen/valuation`
（`save_year(..., force=True)` 会覆盖已有文件）。

后果：一旦有人跑 `python scripts/run_download.py --redownload valuation`
（该命令就写在脚本自己的 docstring 里），那个股票的文件就变成
"亿元 + turnover" 口径 —— `factors/panel.py` 取 `turnover_rate` 会全空，
`total_mv` 缩小 1 万倍，而**市值因子、行业中性化、组合权重全部用它**。
这是配置注释里点名的"双重复权"同类事故。

**当前数据未被污染**（抽样 400 文件 + 全库中位数：71,952 文件全部
`turnover_rate`、中位市值 509,971 万元 ≈ 51 亿元）。已修：
- 去掉换算与改名，严格保持 tushare 原样（万元 / `turnover_rate`）
- `_from_baidu` 回退路径同样修了两处：akshare 的总市值是**亿元** → ×1e4；
  且它只给 3 个字段，**必须把缺的列补成 NaN**，否则那些文件列不一致，
  任何 `read_parquet(glob)` 选到缺列都会抛 `schema mismatch`

**④ 门禁补强（本轮新增的三条，都是"能提前发现上面这类问题"的）**

1. **逐列存在性**：`count(*)` 不引用任何列，所以**缺列的文件不会让查询失败**。
   改为对 `required` 里每一列单独 `SELECT count(列)` —— 缺列立刻抛错。
2. **单位中位数下界**：原来的 `units` 只设上界，而"亿元污染"的数值**更小**，
   照样落在 `[0, 1e11]` 内。给 `total_mv` 加中位数下界 1e4 万元 ——
   正常中位数 5e5，被换算过会掉到 ~50，差 4 个数量级。
3. **全库列一致性**：逐数据集比对文件间的**列名集合**（不比类型 ——
   `financial`/`dividend` 逐文件 INTEGER/DOUBLE 不同是正常的）。
   带**声明式白名单**，只放过上表里那 3 处已声明的分裂；
   任何**新的**未声明分裂都会失败。

**⑤ 其他清理**

- `db/_MANIFEST.json`（B13）：原先手写、无生成方无读取方，内容已与
  `config.RECIPES` 漂移（规则少了三条、`producer` 不一致）。改为
  `config.write_manifest()` 生成，`setup_database()` 每次重建。
- `database/query.py`（B14）：零调用方，且自建连接绕过 `connect_duckdb()`
  （进度条刷 stderr）、`create_views()` 用全目录递归 glob 会在
  `stocks`/`industry` 上抛 schema mismatch 并用 `except Exception: continue`
  吞掉。已就地标注"无调用方 + 三条不要用的理由"。
- `joinquant/data.py::_load_calendar`（B14）：零调用方（`trade_days()` 已改用
  面板日期），已标注。
- 验证了**增量更新与全量重建逐行一致**（对 `year=2025` 的 5,499 个文件 /
  1,313,872 行做 A/B，`limit_up`/`limit_down` 完全相同，含 limit 为空的
  上市初期窗口）—— 这条保证了日常更新不会偷偷改坏数据。
