# 聚宽策略移植报告

> 把用户引入的两份聚宽（JoinQuant）策略移植到本项目，在 **2024-01-01 ~ 2025-12-31**
> 区间回测，用于与聚宽平台的结果对照、验证本项目架构的正确性。
>
> 移植原则：**策略主体一行不改**，只把 `from jqdata import *` 换成本项目的
> `from joinquant import *`。这样回测差异只可能来自**数据**与**撮合**，便于逐项归因。

## 一、结论先行

| 项 | 结果 |
|---|---|
| 移植方式 | 策略代码逐行保留，只替换 import（`scripts/gen_jq_platform.py` 自动生成） |
| 覆盖的聚宽 API | 约 40 个（调度 / 上下文 / 行情 / 财务 query DSL / 下单 / 设置 / 日志） |
| 撮合与账本 | **复用本项目自己的** `Portfolio` / `SimulatedBroker` / `MarketRules`，不另起一套 |

## 三、兼容层设计

```
joinquant/
├── data.py     JQData：行情/财务/指数/ETF 的本地实现 + pandas 1.x 兼容
├── api.py      API 表面（g / context / 下单 / 调度 / query DSL）+ 事件循环
└── __init__.py 导出，使 `from joinquant import *` 等价于 `from jqdata import *`
strategies/jq/
├── guojiu_smallcap.py       v1 移植版（372 行，主体与原版逐行一致）
└── guojiu_smallcap_v2.py    v2 移植版（405 行）
scripts/gen_jq_platform.py    自动生成移植文件
scripts/jq_backtest.py       回测 CLI
tests/test_joinquant.py      17 项测试
```

### 3.1 事件循环

逐交易日、按时间顺序执行 `run_daily` / `run_weekly` 注册的任务：

```
09:05  prepare_stock_list     （读昨日涨停、判断是否可交易日）
10:00  sell_stocks / time_choosing
10:01  position_adjustment
10:05  check_remain_amount
14:00  trade_afternoon        （涨停开板卖出、余额补买）
14:50  close_account          （空仓月清仓）
```

- `run_weekly(func, N)`：`N` = **每周第 N 个交易日**（不是"周 N"）。
  2024-01-01 是元旦，那一周第 2 个交易日是 **1 月 3 日（周三）**，有测试覆盖。
- 单个任务抛异常**不终止回测**（与聚宽一致），但会记进「拒绝委托」并带 traceback。

### 3.2 撮合复用本项目执行层

JQ 的 `order_target_value` → 本项目的 `Portfolio.buy/sell` + `SimulatedBroker` + `MarketRules`：

| 聚宽语义 | 本项目实现 |
|---|---|
| `order_target_value(code, v)`，按手取整 | `max_affordable_size` / `sellable_size`，`lot_size=100` |
| T+1（当日买入当日不可卖） | `Portfolio.new_day()` + `sellable_size()` |
| 涨停买不进 / 跌停卖不掉 | `MarketRules.check_buy / check_sell`（封板口径） |
| 佣金 / 印花税 / 最低佣金 | 按策略自己的 `OrderCost` 传入 |
| 滑点 | `FixedSlippage(x)` / `PriceRelatedSlippage(x)` → 本项目单边 = **x/2**（聚宽口径是双边） |

## 五、移植中修掉的 6 个兼容性缺陷

这些**都不是策略逻辑问题**，而是"聚宽 API → 本地实现"的落差；每一个都会让策略
静默不交易，所以必须逐个消掉才有对照价值。

| # | 问题 | 症状 | 修法 |
|---|---|---|---|
| 1 | **pandas 3 移除了整数索引的位置回退** | `last_prices[stock][-1]` 抛 `KeyError: -1`，v1 的 84 次调仓全挂。聚宽跑的是 pandas 1.x，`s[-1]` 是位置索引 | 提供 `LegacySeries`，整数键找不到标签时回退到 `iloc` |
| 2 | **`context.portfolio.positions` 不是普通 dict** | 聚宽对未持仓代码返回 0 持仓对象，策略写的是 `positions[stock].total_amount == 0`；普通 dict 直接 KeyError（506 次拒绝） | 用带 `__missing__` 的 `_Positions` |
| 3 | **`get_price` 不支持指数/ETF** | `get_price('399101.XSHE')` / `get_price('511880.XSHG')` 抛 KeyError —— 它们不在股票面板里 | 增加 `any_close()`：股票走面板、指数走重建、ETF 走合成 |
| 4 | **`get_price` 的 1 分钟分支方向搞反** | `current_bar()` 返回的是「字段 × 代码」，按「代码 × 字段」取列 → `KeyError: 'open'`（8 次） | 改成按字段行取 |
| 5 | **`query` DSL 漏取过滤字段** | 策略写 `query(valuation.code).filter(income.operating_revenue > 1e8)`，只按 SELECT 取数会让过滤条件**被静默跳过**，把不合格的股票放进来 | 取数列 = SELECT ∪ WHERE |
| 6 | **基准序列只取了 1 个点** | `index_close(..., count=1)` 导致组合与基准没有重叠交易日，画图直接报错 | 取全序列 |
| 7 | **`initialize` 里看到的日期是面板首日** | 面板为预热多带一年多历史，`context.current_dt` 指向预热期，策略在 `initialize` 里算出的 `g.trading_day` 落在 2022 年 → 整个回测一次都不调仓 | `run()` 在调用 `initialize` 前先把 `current_dt` 设成**回测起始日** |
| 8 | **`get_trade_days` 返回 Timestamp** | 策略比较 `today == g.trading_day`，其中 `today` 是 `datetime.date`；`Timestamp == date` **恒为 False**，调仓日永远不成立，v2 全程持 ETF（波动 0.02%） | 返回 **`datetime.date` 列表**（聚宽口径） |
| 9 | **财务 glob 读错报表子集**（第八节 · 静默） | `frozen/financial/year=*/` 下 `balance_*`/`profit_*`/`cashflow_*` 三张表被一把读进来，去重后系统性留下资产负债表行 -> `get_fundamentals` 的 `income.*` 恒为 NaN -> 选股结果恒为空 -> **两个策略全程空仓买货币 ETF**。本地 +2.36% vs 平台 +185.52% | glob 限定 `profit_*`；抽出 `profit_parquet_glob()` 供测试断言前缀 |
| 10 | **`_frame()` 未知字段静默退回 close**（第八节 · 静默） | `get_price(fields=['close','high_limit'])` 里 `high_limit` 拿到的是收盘价 -> `close == high_limit` 恒真 -> `g.yesterday_HL_list` 等于全部持仓 -> 次日 14:00 **每个持仓每天都被"涨停打开卖出"**（v2 五个月 173 次卖出 / 3 次继续持有，收益 +257% -> +1.3%） | 未登记字段返回**全 NaN**（含 `high_limit`/`low_limit` 接真实涨跌停面板） |
| 11 | **`get_price(frequency='1m')` 取列方向反了**（第八节 · 静默） | `current_bar()` 实际是 index=代码 / columns=字段，代码按反方向取 -> 每个字段都落进 `else np.nan` -> `close < high_limit` 恒 False（NaN 比较）-> "涨停打开就卖、次日回补"这条路径**完全死掉**（本地 v1 只有 29 个个股成交日，平台 89 天） | 按真实方向取，并让 `high_limit`/`low_limit`/`pre_close` 走各自真值来源 |

另外两处体验问题：异常只记 `KeyError` 不带 key 和行号（现已带 traceback 与 `@文件:行号`）；
`_Positions` 访问未持仓不应写入字典（有专项测试）。

### 6.3 ⚠️ 关于 511880（银华日利）的口径陷阱

下载真实日线后发现一个**反直觉的事实**：511880 是**货币 ETF，价格恒在 100 附近**，
收益靠"份额折算"发放而不是价格上涨 —— 2024-2025 真实价格累计只有 **−0.036%**，
而原先按"年化 2% 现金等价物"合成是 **+4.0%**，相差 4 个百分点。

- **经济上**：合成口径更准（拿到了货币收益）
- **对照聚宽时**：应当用**真实价格** —— 聚宽回测同样不处理份额折算，
  它的 ETF 持仓也近似零收益

当前实现是**优先真实日线**，所以现在与聚宽口径一致。
若要看"经济上正确"的版本，把 `joinquant/data.py` 的 `etf_close` 改回合成即可。

### 6.4.1 交易记录 / 收益分析导出（对齐聚宽那两份文本）

聚宽回测页可以导出「交易记录」和「收益分析」两份文本。**我们也导出同构的文件**，
否则净值对不上时无法逐笔核对"这笔到底成交没有、为什么没成交"：

```
results/jq/交易记录_{策略}_{区间}.txt        与聚宽同列同序（制表符分隔）
results/jq/委托失败明细_{策略}_{区间}.txt    我们**单独一份**（聚宽混在成交记录里）
results/jq/收益分析_{策略}_{区间}.txt        与聚宽同构的指标表
results/jq/成交明细_{策略}_{区间}.csv        机器可读（含方向符号）
results/jq/成交回合_{策略}_{区间}.csv        FIFO 配对：持仓天数 / 毛利 / 费用 / 净利
```

实现在 `analytics/trade_log.py`，特点与聚宽导出有两点**有意的差别**：

1. 聚宽的成交记录里**含未成交委托**（成交数量 0、成交价为空）。我们把它拆成
   独立的「委托失败明细」（来自引擎的 `reject_log`）—— 混进成交里会让
   "成交笔数 / 成交额 / 换手"这些统计口径变味。
2. 聚宽记的是**委托时间**，我们的引擎只有成交日；默认按成交时点口径填
   （`next_open` → 09:30，`same_close` → 15:00）。

导出自带**对账**（`audit_trades`）：现金变负 / 持仓变负（卖超）/ 非整手 /
成交日不在权益曲线的交易日上，任何一条不过就直接打在回测输出里 ——
成交记录本身不可信时，任何逐笔归因都不成立。

同一套导出已接到项目自己的策略上（`scripts/multifactor_backtest.py`、
`scripts/sector_rotation_backtest.py`），不再只是聚宽移植的附属品。

### 6.5 已知限制

| 项 | 说明 |
|---|---|
| **成交价为日线近似** | 上午任务用开盘、下午（14:00/14:50）用收盘；聚宽是分钟撮合。这是与聚宽差异的**首要来源** |
| **末尾 2 次调仓取不到日期** | v2 在回测最后会找"下个月的第一个交易日"，超出面板覆盖范围 → `IndexError`，那 2 期不调仓。试过改用交易所日历（覆盖到 2027）反而让策略状态机卡死，故保持用面板日期 |
| 微盘股指数 | 万得指数 tushare 没有，v2 仍用代码自带的 `399101.XSHE` 分支 |

### 与聚宽对照的建议步骤

> 已经在第八节做过一轮完整对照，这里保留为**下次换策略时的操作清单**。

1. **先核对基准**：本地 399101 累计 **+37.80%**，平台 **+36.82%** —— 对得上，
   说明指数口径没问题（第八节）。
2. **再核对成交行为**（比净值更早暴露问题）：**成交笔数、个股成交日数、
   每期持股数**。本次就是靠"v1 本地只有 29 个个股成交日，平台有 89 天"
   定位到第三个 bug 的。`results/jq/对照_逐笔.txt` 有分月表。
3. **对不上就先怀疑数据读取，再怀疑撮合**：100pp 量级的差一定是代码错；
   几个百分点的差才轮到 F1/F6。查法：把策略真正用到的字段（财务、涨跌停、
   成分）单独取出来看一眼**有没有值**——三次踩坑都是"整列为空/整列等于别的列"。
4. **最后比净值**：剩余差异应能由第四节第 1 条（分钟撮合 vs 日线开盘/收盘）
   解释。可以把 `--fill open` / `--fill close` 各跑一遍，看哪一端更接近聚宽。

## 八、与聚宽平台的逐项对照（2026-09）

用户在聚宽平台上用**同一份策略、同一区间、同一本金**跑了对照实验，
导出了「交易记录」与「收益分析」，放在 `jq_platform/`。
本节是逐项对比的结论。

### 8.1 平台侧数据

| | v1（动态持仓/止损线9/单价≤50） | v2（中证全指+择时） |
|---|---|---|
| 策略收益 | **+185.52%** | 未导出（文件为空） |
| 年化 | +71.74% | — |
| 基准收益 | +36.82%（399101） | — |
| 夏普 / 索提诺 | 2.129 / 2.829 | — |

那是平台侧的拒单（涨跌停 / 停牌），正好对上我们引擎的 `reject_log`。

### 8.2 本地侧（修完三个 bug 之后）

| | v1 本地 | v1 平台 | v2 本地 | v2 平台(重建) |
|---|---|---|---|---|
| 累计收益 | **+195.41%** | +185.52% | **+224.77%** | +218.14%※ |
| 年化 | +75.76% | +71.74% | +84.65% | — |
| 夏普 | 1.994 | 2.129 | 2.742 | — |
| 最大回撤 | −21.77% | 16.52% | −11.76% | — |
| 成交笔数 | **239** | **239** | 507 | 537 |
| 个股成交日 | 93 天 | 89 天（重合 72%） | 79 天 | 82 天（重合 76%） |

※ v2 的平台「收益分析」是空文件，所以平台净值由**成交记录重演**得到
（`从 100,000 起逐笔推现金与持仓，用本库收盘价重估`）。这套重演在 v1 上
复现了 +184.57% vs 官方 +185.52%（**偏差 −0.95%**），可信度有据；
但它毕竟不是官方数字，只能当参考。

**逐日/逐月收益相关性**：v1 日 +0.825 / 月 +0.739；v2 日 +0.832 / 月 +0.765。
月频超额（平台 − 本地）均值：v1 −0.29%（月度标准差 6.08%）、v2 −0.11%（4.85%）。

**持仓重合度**（月末持仓的 Jaccard，均值）：v1 约 0.35（0.00~0.83）、
v2 约 0.35（0.17~0.76）—— 两头**选中的是同一批票的概率不低，但绝不是同一批**。
这与"按市值升序取最小的 3~6 只"这种**对数据极敏感的排序型选股**一致：
财务数据差一行、成分快照差一个月，名单就会整体错位。

### 8.3 三个把结论彻底带偏的 bug（都不是"近似"）

第一轮对照的本地结果是 **+2.36%**，平台是 **+185.52%**。差的不是撮合保真度，
是三个**静默**的读取错误。它们的共性是：**出错时不抛异常，而是返回一个
"看起来正常"的值**，于是策略照常运行、回测照常出数，只是数字没有意义。

| # | 位置 | 静默返回了什么 | 策略表现 | 单独造成的偏差 |
|---|---|---|---|---|
| 1 | `joinquant/data.py::_load_financials` | `frozen/financial/year=*/` 下三张报表被一起读，`drop_duplicates(keep="first")` 系统性留下**资产负债表**行 -> `income.*` 全 NaN | 国九条筛选（净利润>0、营收>1亿）恒为 False -> 选股结果恒空 -> **全程空仓买货币 ETF** | v1 −183pp（+2.36% vs +185.52%） |
| 2 | `joinquant/data.py::_frame` | 未登记字段 `.get(field, self._close)` -> `high_limit` 返回**收盘价** | `df['close']==df['high_limit']` 恒真 -> `yesterday_HL_list` = 全部持仓 -> **每个持仓每天被"涨停打开卖出"** | v2 +257% -> +1.3%；v1 成交日 93→267 |
| 3 | `joinquant/api.py::get_price(frequency='1m')` | `current_bar()` 的行列方向搞反 -> 每个字段都取不到 -> **整列 NaN** | `close < high_limit` 恒 False（NaN 比较）-> "涨停打开就卖、次日回补"这条路径**完全死掉** | v1 成交日 29 vs 平台 89 |

三者**互相掩盖**，这是最坑的地方：

- bug 1 让策略根本不选股，所以 bug 2/3 在 v1 上看不出影响；
- bug 3 让 `check_limit_up` 永远走 else 分支，**恰好把 bug 2 的"恒真"盖住**；
- 只修 bug 1，v1 到 +121%（看着挺合理）；只修 bug 1+3，v2 崩到 +1.31%
  （bug 2 暴露了）；**三个一起修**才得到 +195.41% / +224.77%。

复现路径（迁移经验）：**"看着合理"的中间结果最有欺骗性**。判据只能是
"与平台差多少"以及"策略行为（成交日数、持股数、换手）像不像"，
不能只看净值曲线好不好看。

### 8.4 剩下的差异归因

三个 bug 修掉之后，v1 的成交笔数与平台**完全相同（239 vs 239）**，
成交日重合 72%、日收益相关 0.825 —— 这说明**兼容层的行为已经对上了**，
残差主要是逐笔价格差。按影响从大到小：

| 来源 | 本次实测的量级 | 说明 |
|---|---|---|
| **F1 成交时点** | 月频超额标准差 6.08%（v1）/ 4.85%（v2） | 平台是分钟撮合，我们上午用开盘、下午（14:00/14:50）用**收盘**。注意：14:00 那批委托我们用**当日收盘价**成交，这既是近似也是**轻度前视**（收盘价 14:00 还不知道），登记在 `docs/日线局限与分钟级扩展痛点.md` |
| **F6 指数成分** | 直接决定选股名单 | 我们只有**月末权重快照**，月中调整无法还原；而这套策略是"按市值升序取最小 N 只"，名单对成分边界极敏感 —— 持仓重合度只有 0.35 |
| **F2 v2 择时指数** | v2 2024-03/04 各差 10~14pp | 万得微盘股指数 tushare 拿不到，改用代码自带的 `399101` 分支 |
| **F7 涨跌停/ST 判定** | v1 被拦 17 笔 / v2 7 笔 | 我们按本框架口径算，平台用自己的；实测拦截以"跌停卖不掉"为主 |
| **B8 货币 ETF 份额折算** | 两边都不处理，口径反而一致 | 见 6.3 |
| F4 回测末尾 2 次调仓 | v2 少 2 期 | 已登记 |

**结论**：本地与平台已经在同一个量级、同一批成交节奏上；v1 差 9.9pp、
v2 差 6.6pp（重建口径），且本地略高 —— 方向上与"我们用收盘价成交"
（比 14:00 的分钟价更有利）一致。**再往下压差异必须上分钟数据**，
那是 `docs/日线局限与分钟级扩展痛点.md` P1/P2 记录的天花板，不在本项目范围内。

### 8.5 诚实声明

- v2 的平台指标是**重建**的，不是官方导出；v2 官方「收益分析」文件为空。
- v1 的重建偏差 −0.95%，来自：成交记录末行被截断、导出的现金为 −109 元
  （说明最后一两天还有未导出的成交）、以及分红/份额折算两边都不处理。
- 持仓重合度是按**月末**快照算的，月中差异会比这个大。
- 本节的对照只覆盖 2024-01-01 ~ 2025-12-31 一个区间、一套参数，
  不足以断言"兼容层在所有策略上都对"。
