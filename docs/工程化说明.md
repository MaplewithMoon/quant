## 1. Git 版本控制

### 1.1 它解决什么问题

在初始化之前，这个项目**没有任何版本历史**。直接后果你已经见过一次：`database/`、`data/`、`backtest/` 等 6 个核心包在某次操作后消失，且无从事后确认"删了什么、什么时候删的、原来长什么样"，只能靠一个恰好存在的 zip 备份救回来。Git 之后，这类事故变成 `git checkout -- <文件>` 一条命令。

具体能力：
- **回滚**：改坏了随时退回任意历史版本
- **对比**：`git diff` 看清"这次改了什么"
- **分支**：试验性重构可以开分支，不影响主线
- **可追溯**：每行代码是谁、什么时候、为什么改的
- **安全网**：`git stash` 临时保存未完成的改动

### 1.2 当前配置与一个必须改的地方

```powershell
git config user.name    # → yiwen
git config user.email   # → yiwen@localhost
```

⚠️ **这两个是占位符，提交记录里会永久留下这个身份。** 如果你之后要推到 GitHub，请先改成你自己的：

```powershell
git config user.name  "你的名字"
git config user.email "你的GitHub邮箱"          # 建议用 GitHub 账号绑定的邮箱

# 修正已经产生的 3 个提交的作者信息
git rebase -i --root                            # 或直接：
git commit --amend --reset-author --no-edit     # 只改最后一个
```

其它已设置的仓库级配置：

| 配置 | 值 | 原因 |
|---|---|---|
| `core.quotepath` | `false` | `git status` 里中文文件名正常显示，不再显示成 `\346\226\207` |
| `core.autocrlf` | `false` | 不在检出时把 LF 转成 CRLF |
| `core.eol` | `lf` | 工作区统一 LF |

### 1.3 常用命令速查

```powershell
# ---- 看状态 ----
git status                      # 哪些文件改了/新增了
git status --short              # 精简输出
git diff                        # 未暂存的改动
git diff --staged               # 已暂存的改动
git log --oneline -20           # 最近 20 条提交
git log --stat -1               # 最近一次提交改了哪些文件
git show 0633933                # 看某个提交的完整内容

# ---- 提交 ----
git add 具体文件.py              # 暂存指定文件（推荐，比 -A 更可控）
git add -A                      # 暂存全部改动
git commit -m "说明"            # 提交
git commit -am "说明"           # 暂存已跟踪文件的改动并提交（不含新文件）

# ---- 撤销 ----
git restore 文件.py             # 丢弃工作区改动（危险，不可恢复）
git restore --staged 文件.py    # 取消暂存，保留改动
git commit --amend              # 修改最后一次提交（未推送时可用）
git revert <commit>             # 生成一个"反向提交"来撤销历史提交（已推送时用）

# ---- 分支 ----
git switch -c feature/因子库     # 新建并切到分支
git switch main                 # 切回主线
git merge feature/因子库         # 合并分支

# ---- 临时保存 ----
git stash                       # 把未提交的改动收起来
git stash pop                   # 取回来
```

### 1.4 推荐的日常工作流

```powershell
# 1. 开工前确认干净
git status

# 2. 改代码 ...

# 3. 看一眼改了什么

# 4. 跑测试（本地先过一遍，别等 CI）

# 5. 提交
```

### 1.6 7.2GB 的数据库为什么不进 Git

`db/` 现在约 7.2 GB、近 15 万个 parquet 文件。放进 Git 的后果：
- 每次提交都可能有几万文件变动，`git status` 卡死
- `.git` 目录会膨胀到十几 GB，且**历史里的大文件永远删不掉**（除非重写历史）
- GitHub 单文件 100MB、单仓库推荐 1GB 上限，直接推不上去

**正确做法**：
```powershell
# 数据用独立方式备份（外部硬盘 / NAS / 对象存储）
robocopy D:\quant\db E:\backup\quant_db /MIR /Z /R:2 /W:2
```

**在另一台机器恢复数据**（从零重建，需 tushare token）：
```powershell
python scripts/download_tushare_raw.py        # frozen/daily_raw 原始价
python scripts/download_frozen_tushare.py     # adjust/st/valuation/etf/options
python scripts/rebuild_cleaned.py             # 重建清洗层 db/daily
python scripts/daily_update.py                # 之后每日增量更新
```

`db/frozen/` 是"不可变可信源"，`db/daily`、`db/limit` 都可以从它重建——所以**只要护住 frozen 层，其它都能再生**。

## 2. `.gitignore` —— 哪些文件不进版本库

### 2.1 原理

Git 会跟踪仓库目录下的**所有**文件，除非被 `.gitignore` 排除。规则按行匹配（支持通配符），`/` 结尾表示目录，`!` 开头表示"反向排除"。

关键点：**`.gitignore` 对被跟踪过的文件无效**。如果某个文件已经被 `git add` 过，之后再写进 `.gitignore` 也没用，必须先 `git rm --cached`。

### 2.2 逐段说明

| 段落 | 忽略内容 | 为什么 |
|---|---|---|
| 量化数据库 | `db/` | 7.2GB 数据，可由脚本重建；参考 1.6 节单独备份 |
| 密钥与凭证 | `tushare_token.txt`、`.env`、`*.key`、`*.pem`、`secrets.json` | **一旦推到公开仓库，token 会被爬虫秒抓**。`database/token.py` 会读 `database/tushare_token.txt` 或根目录同名文件 |
| 第三方/无关目录 | `others/`、`vnpy-4.4.0/`、`方正证券FQT交易客户端-40438/` | 前两者是外部源码/实验区，后者是券商客户端（含大量自带库文件） |
| Python 产物 | `__pycache__/`、`*.py[cod]`、`*.egg-info/`、`build/`、`dist/` | 编译/打包生成，无版本价值 |
| 虚拟环境 | `.venv/`、`venv/`、`env/` | 体积大且与机器绑定 |
| 测试缓存 | `.pytest_cache/`、`.ruff_cache/`、`.mypy_cache/`、`.coverage`、`htmlcov/` | 工具缓存 |
| 运行产物 | `lookahead_report.txt`、`半导体轮动_*.csv/png`、`*.duckdb`、`*.log` | 每次回测都会重新生成 |
| 备份归档 | `quant_*.zip`、`*.zip`、`*.7z`、`*.rar` | 你那个 390KB 备份 zip 就不进库 |
| 编辑器/系统 | `.vscode/`、`.idea/`、`Thumbs.db`、`.DS_Store` | 个人环境差异 |
| 迁移脚本 | `.deps/` | 本次 Python 3.12→3.14 的一次性脚本与日志 |

### 2.3 怎么验证某个文件会不会被忽略

```powershell
git check-ignore -v db/frozen/_MANIFEST.json     # 会打印命中的规则和行号
git check-ignore -v tests/test_loader.py         # 无输出 = 会被跟踪
git status --ignored --short | Select-Object -First 20   # 列出被忽略的文件
```

### 2.4 想纳管 `others/` 怎么办

`others/sanhu`、`others/smart_money` 里如果有你想版本化的代码，把 `.gitignore` 里这两行删掉或改写：

```gitignore

```
或只排除大文件、保留源码：
```gitignore

```

改完执行 `git add others/ && git commit -m "chore: 纳管 others 实验代码"`。

### 2.5 已经被跟踪的文件，如何改成忽略

```powershell
git rm -r --cached db/          # 从索引移除，但保留磁盘文件（--cached 很重要）
git commit -m "chore: 停止跟踪 db 目录"
```

## 3. `.gitattributes` —— 怎么处理文件内容

### 3.1 作用

`.gitignore` 管"**要不要**这个文件"，`.gitattributes` 管"**怎么处理**这个文件"。它主要解决两类问题：行尾符、二进制识别。

### 3.2 当前规则

```gitattributes
* text=auto eol=lf          # 文本文件统一 LF
*.parquet binary            # 以下按二进制处理，不做任何转换
*.pdf binary
*.exe binary
*.pyd binary
...
```

### 3.3 为什么统一 LF

Windows 默认 CRLF，Linux 默认 LF。如果不统一：
- 同一个文件在不同机器上"看起来全变了"，`git diff` 整文件标红，真正的改动被淹没
- CI 在 Linux 上跑，如果仓库里混着 CRLF，容易触发莫名其妙的 diff

统一成 LF 后：仓库内、Windows 工作区、Linux CI 全都是 LF，`git status` 只反映真实改动。

**副作用**：如果你用记事本之类的编辑器保存文件，可能被改回 CRLF，此时 `git diff` 会提示。VS Code 右下角可以点一下切换成 LF。

### 3.4 二进制标记为什么必要

如果不标记，Git 会尝试对 `.parquet` 做行尾转换和文本 diff——既浪费时间又可能**损坏文件**。标记为 `binary` 后，Git 只做字节级存储。

## 4. `pyproject.toml` —— 项目的唯一事实来源

### 4.1 它取代了什么

以前依赖写在 `requirements.txt`，测试配置可能散在 `pytest.ini`，代码风格配置在 `.flake8`……现在全部集中到一个标准文件（PEP 518/621）。好处：任何工具（pip、pytest、ruff、IDE、CI）都读同一个文件，不会再出现"我本地能跑你那边不行"。

### 4.2 逐节说明

| 小节 | 作用 |
|---|---|
| `[build-system]` | 声明用 setuptools 打包。`pip install -e .` 时 pip 会先装这里的 `requires` |
| `[project]` | 名称、版本、描述、`requires-python`、分类器等元数据 |
| `dependencies` | **运行依赖**。只写直接依赖，传递依赖交给解析器 |
| `[project.optional-dependencies]` | 可选功能组：`dev`（pytest+ruff）、`talib`、`live`（vnpy） |
| `[tool.setuptools] packages` | **显式**列出要安装的 12 个包。因为 `data`/`config`/`utils` 这些名字太通用，显式声明可避免误把 `db/`、`others/` 打包进去 |
| `[tool.setuptools] py-modules` | 把根目录 `main.py` 也纳入 |
| `[tool.pytest.ini_options]` | `testpaths=tests`、`pythonpath` 让 `from mocks import ...` 可用 |
| `[tool.ruff]` / `[tool.ruff.lint]` | 静态检查的规则与排除目录 |

### 4.3 常用命令

```powershell
# 推荐：可编辑安装 + 开发工具（已在本机执行过）
pip install -e ".[dev]"

# 连 ta-lib 和 vnpy 一起装
pip install -e ".[dev,talib,live]"

# 只装运行依赖
pip install -e .

# 从锁文件精确复现环境
pip install -r requirements.lock.txt

# 查看本项目已安装的元数据
pip show quant

# 卸载项目本身（不影响第三方依赖）
pip uninstall quant
```

> 国内网络建议加镜像：`pip install -e ".[dev]" -i https://pypi.tuna.tsinghua.edu.cn/simple`

### 4.4 「可编辑安装」做了什么（已执行）

`pip install -e .` 做了两件事：
1. 在 site-packages 里注册一个指向 `D:\quant` 的链接（`quant 0.1.0`）
2. 于是**任何目录下**都能 `import database` / `import data` / `import backtest`

实测验证：

依赖版本未被改动：numpy 2.5.1 / pandas 3.0.3 / pyarrow 25.0.1 / duckdb 1.5.5。

### 4.5 关于 `ta-lib` 的版本下限

`talib = ["ta-lib>=0.8"]` 为什么不是 0.6？

因为 3.12 时代的 `ta-lib==0.6.4` **没有 Python 3.14 的预编译包**，安装时会退回源码编译，然后报：
```
fatal error C1083: 无法打开包括文件: "ta_libc.h"
```
（缺 TA-Lib C 库头文件）。0.8.0 有 cp314 wheel，装上即用。已实测 `talib.SMA` 计算正确。

## 5. `requirements.lock.txt` —— 精确复现

`pyproject.toml` 里写的是**区间**（`pandas>=3.0`），保证灵活性；`requirements.lock.txt` 记录的是**当前这台机器上验证过的精确版本**（78 个包，`pandas==3.0.3` 这种）。

用途：
- 换机器 / 重装系统后，一条命令回到完全一样的环境
- CI 上想测试"锁定版本是否正常"时可用
- 出问题时能确认"当时用的是哪个版本"

更新方式（在你确认新版本没问题之后）：
```powershell
pip freeze > requirements.lock.txt
git add requirements.lock.txt
git commit -m "chore: 更新依赖锁文件"
```

## 6. CI —— 自动化的守门人

### 6.1 它解决什么问题

「在我机器上是好的」是工程里最贵的谎话。CI 每次都在一台**全新的干净机器**上：装 Python → 装依赖 → 跑测试。它能抓住：

- 你写了个依赖但**忘了加进 `pyproject.toml`**（本地装了所以没发现）
- 代码里写死了 Windows 路径（`f.split("\\")` 这类），到 Linux 就崩
- 改动**悄悄改变了回测结果**（测试会失败）
- 换了 Python 小版本后某个包不兼容

### 6.2 什么时候触发

| 事件 | 是否触发 |
|---|---|
| `git push`（任意分支） | ✅ |
| 提交 Pull Request | ✅ |
| 网页手动点 Run workflow | ✅ |

同一分支连续 push 时，会自动取消上一次没跑完的任务（`concurrency` 配置），不浪费额度。

### 6.3 两个任务

**job 1 `test`（门禁，失败即 CI 失败）**

矩阵：`ubuntu-latest` + `windows-latest` × Python `3.14`

| 步骤 | 做什么 | 抓什么 |
|---|---|---|
| checkout | 拉代码 | — |
| setup-python | 装 Python 3.14，按 `pyproject.toml` 缓存 pip | — |
| `pip install -e ".[dev]"` | 只按 pyproject 装依赖 | **验证 pyproject 写全了没** |
| `pip check` | 检查依赖冲突 | 版本不兼容 |
| 导入冒烟 | 逐个 import 13 个核心模块 | 循环导入、语法错误、缺模块 |
| `pytest -v` | 13 个单元测试 | 逻辑回归 |
| `run_tests.py` | 项目自带运行器 | 两种入口都可用 |

**job 2 `lint`（只报告，不阻断）**

`ruff check .`，`continue-on-error: true`。现在有 51 条历史问题，先只做提示；清理干净后把 `continue-on-error` 删掉即可转正。

### 6.4 怎么看结果

推送到 GitHub 后：仓库页面 → **Actions** 标签 → 点进某次运行。
- 绿勾 = 通过
- 红叉 = 失败，点进去看哪一步、哪一行报错

### 6.5 在本地复现 CI（最实用的一招）

不用等推送，本地就能跑一遍几乎一样的流程：

```powershell

```

### 6.6 想扩展 CI

- **加 Python 版本**：改 `matrix.python-version: ["3.13", "3.14"]`（注意 `requires-python = ">=3.11"` 是否放得太宽）
- **加自动发版 / 定时跑数据更新**：新增 `.github/workflows/xxx.yml`，用 `on: schedule:` 配 cron
- **让 lint 变硬门禁**：删掉 `lint` job 里的 `continue-on-error: true`
- **加覆盖率**：`pip install pytest-cov`，然后 `pytest --cov=. --cov-report=term-missing`

### 6.7 局限（必须知道）

1. **CI 不跑数据相关脚本**。测试全部用 `tests/mocks.py` 造假数据，不读 `db/`、不联网——这是刻意的，否则 CI 需要 7.2GB 数据和一个 tushare token。所以 `download_*.py`、`daily_update.py`、`clean_data.py`、`semiconductor_rotation.py` 的正确性**CI 覆盖不到**。
2. **token 不能进 CI**。如果以后要跑真实数据，得用 GitHub Secrets 存 `TUSHARE_TOKEN`，通过环境变量注入（`database/token.py` 优先读环境变量，天然支持）。
3. **CI 需要先把代码推到 GitHub 才生效**。当前只是本地仓库。
